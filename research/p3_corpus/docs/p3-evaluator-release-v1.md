# P3 evaluator release v1

## Status

`p3-evaluator-release-v1` is an internal release contract. It is not registered
or publishable in the image-pinned `edullm-data` deployment yet. The research
image installs the exact immutable commit
`38bf831a6c3f445e394784018441fd59288b876c`; that commit's registry has five shipped profiles:

- `pretrain-tokens/v1`
- `eval-results/v1`
- `token-order/v1`
- `sft-conversations/v1`
- `tokenizer/v1`

There is no `text-corpus/v1`. None of the five profiles can losslessly validate
this mixed evaluator payload.

No evaluator selector or other UI is approved. The selected token release pins
one evaluator dependency. Training and post-training evaluation resolve that
dependency transitively.

## Source contract

The packager accepts the transaction root, its canonical `CURRENT` path, and
the registered binary validators. It constructs the accepted
`GenerationCoordinator` and calls `resolve_current(required_siblings=...)` for
all six families; it never accepts a caller-provided manifest/publication
dictionary. The resolver revalidates transaction state, exact manifest fields,
plan root, routes, accounting, validator descriptors, modes, directory
inventory, bytes, rows, logical hashes, and `logical_root_sha256`.

Every native input must be the actual file named by that transaction inventory.
The packager rechecks path, bytes, SHA-256, rows, schema, role, sibling,
generation ID, logical root, transaction inventory SHA-256, `MANIFEST.json`,
and `CURRENT`. Counterfeit re-signed control files, empty plans, removed routes,
and caller-constructed generation bindings fail.

The pooled MML input is loaded with:

```python
load_holdout_contract(path, production=True)
```

This verifies its full inventory, route plan, sidecars, source policy, and roots
at packaging time. The evaluator release contains only the reporting inputs:

- authoritative `heldout/mml.json`;
- package-derived `heldout/mizar.json` and `heldout/atp.json`;
- exposure and drop sidecars.

Mizar and thproofs use the `mizar` projection. prf2 and ENIGMA use the `atp`
projection. There is no thproofs projection.

Projection bytes are regenerated by `canonical_mml_projections()` solely from
the validated authoritative MML manifest. Class IDs, native shard traversal,
names, statement hashes, keys, and output paths are canonicalized before
serialization. The evaluator inventory records each projection as derived from
`semantic/heldout/mml.json`, not as a byte-for-byte copy of the compatibility
projection in the source workspace.

At load time, the packaged authoritative manifest's self-root, artifact
inventory root, source root, source-policy ID/SHA, tokenizer root, production
markers, and ordered source records are revalidated from persisted bytes. The
loader then recomputes the two projections with the package-owned canonical
deriver. It does not call the mutable workspace production-policy resolver or
the semantic package's compatibility-projection helper. A later workspace
policy/code change therefore cannot invalidate an immutable release; changing
any persisted byte or recorded root still fails.

## Flat release layout

The internal transaction release is exactly one payload tree whose logical
paths begin with the single group `evaluator`. Every payload has two path labels,
and the second filename encodes its role:

```text
evaluator/eval-<family>.jsonl
evaluator/heldout-{mml,mizar,atp,metamath,isabelle}.json
evaluator/visibility-<family>.jsonl
evaluator/visibility-corpus-union.jsonl
evaluator/sidecar-mml-{exposure,drop-reasons}.jsonl
evaluator/sidecar-{drop,cohort}-<family>.jsonl
evaluator/sidecar-{verifier,oracle}-<name>.json
evaluator/provenance-{corpus-manifest,corpus-current,tokenizer}.json
evaluator/provenance-source-<family>.json
evaluator/{release-manifest,completion}.json
```

`evaluator/manifest.json` is reserved exclusively for the generated
`edullm-data` group manifest and is forbidden in evaluator payloads. The
evaluator manifest is `evaluator/release-manifest.json`, and the completion
seal names that exact path.

These are internal release logical paths, not a claim that the platform stores
an extra nested dataset abstraction. During publication, `evaluator` is the
first-level group selected by the new profile. The platform creates that
group's own `evaluator/manifest.json`; the internal
`evaluator/release-manifest.json` and `evaluator/completion.json` remain payload
objects in the same group. The platform group-manifest SHA and the internal
release-manifest root are distinct dependency pins.

The manifest requires one unique semantic role for every inventory entry. Roles
must resolve the exact six families and canonical paths; duplicate roles,
family swaps, arbitrary schemas, and deeper paths fail.

## Semantic train visibility

`visibility/*.jsonl` contains sorted semantic-class records, not raw name/hash
pairs. Each record includes:

- semantic class ID;
- all observed native members and raw aliases;
- approved Mizar↔ATP aliases;
- representation-scoped statement hashes;
- families in which the class is train-visible.

For example, `ARTICLE:7` and `t7_article` share
`mml:v1:theorem:ARTICLE:7`. The corpus-union file merges those observations.
This is the representation-aware mechanism needed to classify the 1,425
occurrences missed by exact raw `(name, statement hash)` matching.

## Roots and completion

Every inventory entry has an exact key set and includes logical path, bytes,
rows, SHA-256, schema, generation ID, unique role, the scientific roots,
the source transaction inventory SHA-256, and either:

- an exact transaction source binding; or
- the transaction paths from which a generated visibility file was derived.

`inventory_root_sha256` hashes the canonical ordered inventory.
`manifest_root_sha256` hashes the complete manifest body.
`evaluator/completion.json`
binds both roots, the exact manifest-file SHA-256, dataset identity, generation,
version, and inventory count.

The schemas are:

- `docs/p3-evaluator-release-v1.schema.json`
- `docs/p3-evaluator-release-completion-v1.schema.json`

`write_json_schemas()` deterministically generates both from the same canonical
path→role→schema constants used by runtime. Every inventory path has an exact
`oneOf` branch. Tests import `jsonschema` directly and run with
`uv run --with pytest --with jsonschema`; schema validation is never skipped.

The only approved dataset ID is `eval/formal-proof-premises-500m`. Versions are
`__UNPUBLISHED__` for local inspection or explicit `vN` for production.
`load_release(..., expected_version=...)` requires the caller to select the
expected mode.

## Publication transaction

`EvaluatorReleaseCoordinator` is only an adapter that constructs an accepted
`GenerationPlan` and delegates all writes and publication to
`corpus_generation_transaction.GenerationCoordinator`. Evaluator payloads are
written through `GenerationWriter.write_bytes`; a private accounting carrier
satisfies the transaction's raw/train/eval/drop/heldout routing contract. There
is no evaluator-specific staging, rename, `CURRENT`, recovery, or fault path.

Publication therefore inherits:

- fresh staging;
- validation before visibility;
- immutable `generations/<generation-id>`;
- atomic `CURRENT` replacement;
- directory fsync boundaries;
- the complete shared `PublishPhase` matrix;
- `CommitUncertainError.resolve()` after an uncertain commit;
- transaction-state recovery and quarantine.

`resolve_current()` has no in-memory plan dependency. A fresh process registers
the fixed transaction payload validator, resolves persisted transaction-v2
state, and then verifies the complete evaluator group. This also works after a
commit-uncertain restart.

The determinism suite performs 50 independent clean publications concurrently,
destroys the publishing coordinators, and reloads each tree in a subprocess
with a different `PYTHONHASHSEED`. It also randomizes mapping insertion order
and perturbs the mutable semantic projection helper. All cycles must produce
the same payload-tree hashes, evaluator manifest root, and completion seal;
there is no flaky-retry allowance.

`materialize_release()` is only a local test/pre-publication inspection helper.
Any publication uses the accepted transaction coordinator and secure writer.

## Mandatory token dependency

The token release dependency has exactly these fields:

```json
{
  "role": "evaluator",
  "dataset_id": "eval/formal-proof-premises-500m",
  "version": "vN",
  "manifest_sha256": "<platform evaluator group manifest SHA-256>",
  "evaluator_manifest_root_sha256": "<local evaluator manifest root>",
  "evaluator_seal_sha256": "<evaluator/completion.json SHA-256>"
}
```

`require_token_dependency()` requires caller-expected values for all five pins:
dataset ID, explicit version, platform group manifest SHA-256, evaluator root,
and evaluator seal. There are no defaults. It also verifies that the root and
seal identify the loaded local release.

The platform dependency validator must compare all declared values after
resolving the parent. Merely proving that the dataset/version exists is
insufficient.

## Exact platform-owner changes

### Profile module

Add `src/edullm_data/profiles/p3_evaluator_release_v1.py` with the pinned
module-style profile API:

```python
from __future__ import annotations

import sys

from . import registry
from .base import GroupContext, Violation

NAME = "p3-evaluator-release-v1"
REQUIRED_FIELDS = {
    "manifest_root_sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"},
    "completion_seal_sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"},
    "corpus_logical_root_sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"},
    "semantic_holdout_root_sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"},
}


def check_evaluator_release(context: GroupContext) -> list[Violation]:
    # The platform implementation must port the local load_release checks:
    # exact flat inventory, every object hash/size/rows/schema/role, canonical
    # roots, completion, transaction source bindings, pooled-MML projections,
    # sidecars, visibility JSONL, and all six family routes.
    return verify_evaluator_group(context)


CHECKS = [check_evaluator_release]
registry.register(sys.modules[__name__])
```

`verify_evaluator_group()` is not present in the pinned package; it must be
added with passing and hostile `FakeS3` tests. Returning `[]` without porting
those recomputation checks would violate the profile contract.

Add `"p3_evaluator_release_v1"` to `profiles.registry._SHIPPED`. No family
allowlist or dropdown change is needed.

### Publisher

The publisher must:

1. publish the single `evaluator/` group with the canonical filenames above;
2. accept only that group's exact two-label inventory;
3. stage and promote through transaction-v2 `GenerationCoordinator`;
4. generate the platform-owned `evaluator/manifest.json` group manifest and
   expose its SHA-256 as dependency field `manifest_sha256`;
5. preserve the evaluator root and completion-seal SHA in group metadata.

No generic filename renaming is claimed or required. This is one profile-bound
group, not a dataset-level platform abstraction. The publisher must never
overwrite or rename `evaluator/release-manifest.json`.

### Validator

Gate A must:

1. invoke the new profile checks over every object;
2. reject missing, extra, duplicate-role, deep-path, stale-root, and test-only
   releases;
3. when validating token `depends_on`, compare the declared evaluator dataset,
   version, group manifest SHA-256, evaluator root, and evaluator seal against
   the resolved parent group. `manifest_sha256` means the generated
   `evaluator/manifest.json` SHA; `evaluator_manifest_root_sha256` means the
   canonical root inside `evaluator/release-manifest.json`.

### Reader

The reader must return the selected `evaluator/manifest.json` SHA together with
local paths and explicit `vN`. Token readers resolve
`depends_on[role=evaluator]`; the post-training evaluator uses that same
resolved dependency and calls `load_release(..., expected_version=version)`.

## Later live-code integration

No live integration is included in this change. Remaining actions are:

- `run_eval`: resolve the evaluator dependency before model import/load, verify
  `manifest_sha256` against platform-owned `evaluator/manifest.json`, load
  `evaluator/release-manifest.json` with the dependency's expected `vN`,
  consume semantic visibility and class/cohort paths, and record all five pins.
- token finalizer: require the exact five fields, keep platform
  `manifest_sha256` distinct from `evaluator_manifest_root_sha256`, and compare
  the evaluator corpus logical root with the token source generation.
- platform: ship the profile, publisher, validator, reader, and fixtures
  together; do not add UI.
