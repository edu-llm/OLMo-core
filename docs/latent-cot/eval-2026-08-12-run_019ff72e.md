## 2. The anchors came back inverted, which is the real finding

| Arm | Mode | Overall | D2 | D3 | D4 | D5 (OOD) | D6 | D8 (OOD) |
|---|---|---|---|---|---|---|---|---|
| A1 | `no_cot` | **1.000** | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| A0 | `explicit_cot` | **0.537** | 0.512 | 0.531 | 0.562 | 0.569 | 0.512 | 0.537 |

The held-out set is balanced 80/80 reachable/unreachable at every depth, so **chance is 0.500**.

A1 is the experiment's designed *lower* anchor — answer straight from `question <distill>`, no
reasoning tokens at all. A0 is the *upper* anchor — write the CoT out and then answer. The floor
scored perfectly and the ceiling scored at chance. Both directions are implausible on their own,
and together they say something is wrong upstream of the measurement:

- **A1 = 1.000 at every depth, including D5 and D8, which are out of distribution.** Training
  depths are 2/3/4/6; D5 and D8 appear only in the held-out set. A model that generalises
  perfectly to unseen depths *without* emitting a single reasoning token is not doing search. The
  generator asserts `Train/heldout leakage (validator dedup key): 0 shared`, so there are no exact
  duplicates — but a dedup key over whole examples would not catch an answer-revealing feature in
  the encoded `direct_input_ids` view A1 reads. That view is where to look first.
- **A0 = 0.537 is at chance**, and partly my fault (see finding 3) — but only partly, and the
  residue is unexplained.

## 3. `--max-new-tokens 64` was too small, and that is my error

I set the cap from the longest teacher CoT measured as **whitespace words** (56). The dolma2
tokenizer emits roughly 1.7× that for this content — multi-digit node ids and the `|` frontier
separators do not survive as one token each. Measured properly, over the same 960 examples, the
tokens A0 must generate to reach `<distill>`:

```
mean 47.6   median 44   p95 89   max 103
226 of 960 examples (23.5%) need MORE than 64
```

So a quarter of A0's evaluations were truncated before reaching `<distill>`, and their answer was
read at whatever position generation stopped at. `--max-new-tokens 112` would clear the observed
maximum; the flag's own help text still repeats the wrong 56 and must be corrected with it.

**But this does not explain A0's score.** Truncating 23.5% of examples to chance while the rest
worked would land around `0.765·p + 0.235·0.5`; for the total to be 0.537, `p` would have to be
about 0.548 — itself chance. So A0 is at chance on the examples it evaluated *correctly* too.
Fixing the cap is necessary and will not rescue this number.

## 4. RESOLVED: the dataset was solvable without search, and that explains both anchors

The leakage check came back positive, and not in the encoding — in the **generator**. `A1`'s
prompt is clean (`question <distill>`, answer read at `<distill>`, no leak). The problem is one
level up: `graph_gen.generate()` gave every unreachable target **zero in-edges**, so

```
"> T" does not appear in the edge list   ==   not reachable
```

Measured on the same 960 held-out examples that produced the table above:

| Surface rule | Accuracy | By depth |
|---|---|---|
| target is an edge destination (`u > T`) | **1.0000** | 1.000 at D2/D3/D4/D5/D6/D8 |
| target appears anywhere in edges | **1.0000** | — |
| target has an outgoing edge | 0.5000 | — |

One substring test solves the task perfectly at every depth. That is the whole explanation of the
inverted anchors: **A1 = 1.000 including OOD depths because a rule that never consults depth
transfers across depth perfectly.** A1 was not reasoning and was never a floor. And it means A0's
chance score is not the anomaly it looked like — the task had no depth axis to be good at.

The generator's own docstring called this a feature ("the target simply has no in-edges, so
concluding 'not reachable' requires exploring the reachable set") while explicitly defending
against the subtler *frontier-depth* leak. Closing the harder leak and leaving the trivial one is
what made it survive review.

**Every number from every run on this branch is vacuous, including both figures in the table
above.** The gates were not merely unmeasured; had the CODI arms survived, the gates would have
been vacuous too, because no arm can show an advantage on a task that needs no search.

### The fix

`generate()` now builds **two equal-length layered chains** per instance — one rooted at the
source, one at an in-degree-zero decoy root — and the classes differ *only* in which chain the
target sits on. Deciding reachability requires tracing the target's ancestors back `depth` levels
to see which root they reach. On the regenerated split every surface rule is at chance:

```
target is an edge destination      0.5000  (D2..D8 all 0.500)
target appears anywhere in edges   0.5000
target has an outgoing edge        0.5000
target in-degree > 1               0.5115
a predecessor of target has a pred 0.5000
target id below midpoint           0.5167
```

Two things fell out of it worth keeping:

- **The classes are now exactly matched pairs.** Nothing in the construction except the choice of
  target consults `reachable`, so one seed yields the *same graph* for both classes with a
  different node named as sink. That is a stronger confound control than the old construction had
  even in intent, and it is asserted in the tests so it cannot be lost quietly.
- **A one-backward-step rule separated the classes at depth 2** in the first attempt, caught by
  the new battery, not by review. Fixed by giving the decoy chain its own level-0 root so the two
  chains are structurally identical. This is why the regression test is a battery of rules rather
  than one assertion —
  `test_no_surface_heuristic_separates_the_classes` requires every rule to stay near chance.

The repaired data is also cheaper: half the nodes now sit on the decoy chain, so frontiers from
the source are narrower and the longest teacher trace fell from **103 tokens to 57**.

### And my `--max-new-tokens` bug is fixed properly

Not by raising 64 to 112, which would have been another magic number one dataset change from
going stale. `eval_arms_from_s3.py` now **derives** the cap from the test data (longest teacher
trace + 8) and prints it. The flag remains as an override, with the failure recorded in its help.

## What to do next, in order

1. **Retrain all five arms on the repaired data** — the only path to either gate, and what
   `.edullm/run.yaml` now holds. The OOM fix is `--batch-size 8` (activations scale linearly;
   38.51 GiB was measured on a 40 GiB A100), helped by the shorter sequences. The eval runs in the
   same job so the gates come back without a second approval.
2. Read `preflight.py`'s output in that run before trusting the arms: it is the pre-registration
   confound gate and it has never run against this dataset.
3. Note that halving the batch halves the effective step, so the unscreened `2e-5` LR is *less*
   anchored than before. Held identical across arms, so it cannot confound the comparison between
   them — it only limits what an absolute number means.
4. Only then is there anything to put on a slide.
