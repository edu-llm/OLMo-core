## 1. Everything before 2026-08-12 is vacuous

`graph_gen.generate()` gave unreachable targets **zero in-edges**, making

```
"> T" absent from the edge list   ==   not reachable
```

Measured on the held-out split: that single substring rule scored **1.0000 at every depth**,
out-of-distribution depths included. The task needed no search, so no arm could have shown a
superposition advantage and the gates would have been vacuous even had the CODI arms survived.

Repaired: two equal-length layered chains per instance, one rooted at the source, one at an
in-degree-zero decoy root, classes differing only in which chain the target sits on. After repair,
every surface rule is at chance:

## 3. Why, measured rather than argued

| Run | batch | peak at OOM | survived |
|---|---|---|---|
| run_019ff280 | 16 | 38.51 GiB | 2h48m |
| run_019ff806 | 8 | 38.72 GiB | ~2 min |

**Halving the batch changed peak memory by 0.2%.** `arm_loss` sums a per-example loss over the
whole batch and returns one tensor, so nothing is freed until the caller's single `backward()` and
every example's teacher forward *and* K=10 student chain are alive at once.

Per-example cost, measured on the repaired data:

| | token-forwards per example |
|---|---|
| A0 (teacher forward only) | 250 mean |
| CODI (teacher + K chain + final) | **2,724 mean, 6,158 max** — 10.9x |

Scaling A0's observed 11.72 GiB gives ~45 GiB of activations at batch 8. Peak therefore tracks the
*longest examples drawn*, not the batch size — which is why batch 16 got lucky for nearly three
hours on shorter data while batch 8 on longer data died immediately.

A correction worth recording: I claimed the repaired dataset would *add* memory margin because the
teacher trace shortened (103 → 57 tokens). Backwards. The two-chain construction puts more edges
in every graph, so prompts lengthened (teacher seq mean 250, max 556), cancelling the batch-8
saving. I measured the trace and asserted the margin without measuring the prompt.

## 4. The fix, and why it is not another guess

`train_arm` now slices each batch and backwards each slice, scaling by `len(slice)/len(batch)`, so
the accumulated gradient is **identical** to one full-batch backward — asserted for A0, A2 and A3
by comparing weights after one step from a shared initialization
(`test_micro_batching_gives_the_same_gradient_as_one_backward`). Effective batch size, LR schedule
and every confound control are untouched. Peak becomes a function of one example (~20 GiB).

The next run also **measures it before committing ten hours**: a two-step probe on one CODI arm
prints its peak and aborts the job above 34 GiB. Three OOM diagnoses in a row were argued from
arithmetic and all three were wrong, so this one is checked on the hardware first.

Also fixed: `PYTORCH_ALLOC_CONF` (torch 2.9 renamed it and ignored the old name while printing a
deprecation notice), per-arm `WANDB_RUN_ID` (all five arms had resumed into one W&B run and
overwritten each other), and a 7-minute heartbeat naming every arm alive/GONE so a dead arm can
never again be invisible behind a 50-line log tail.
