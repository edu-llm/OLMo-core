## 1. How `beta` is produced in `KimiDeltaAttention` — CONFIRMED: `sigmoid`, with a `2*` already present and already wired

`src/olmo_core/nn/attention/recurrent.py:874-876`:

```python
        beta = self.w_b(x).sigmoid()
        if self.allow_neg_eigval:
            beta = beta * 2.0
```

There **is** a flag that makes it `2*sigmoid`, and it is the same `allow_neg_eigval` name. It
defaults `False` (`:687`, and `KimiDeltaAttentionConfig.allow_neg_eigval: bool = False` at `:1088`),
and the config forwards it to the layer at `:1397` (`allow_neg_eigval=self.allow_neg_eigval`).

**The wiring is complete end to end.** Nothing else in the class consults the flag: `grep -n
"allow_neg_eigval"` over `recurrent.py` returns for this class only `:656` (docstring), `:687`
(param), `:708` (assignment), `:875` (the branch above). It is stored and used in exactly one
place. `dispatch_chunk_kda` (`flash_linear_attn_api.py:45-127`) does not take the flag and does not
need to — it receives the already-doubled post-sigmoid `beta` as a plain tensor at `:119`.

## 2. What `allow_neg_eigval=True` changes in `KimiDeltaHouseholder` — CONFIRMED: nothing but beta's range. The two code paths are character-identical.

`recurrent.py:1627-1629`:

```python
        beta = self.w_b(x).sigmoid()
        if self.allow_neg_eigval:
            beta = beta * 2.0
```

Diff against `KimiDeltaAttention:874-876`: **none.** Same three lines, same order, same constant.
As with KDA, the flag appears only at `:1453` (docstring), `:1472` (param), `:1492` (assignment),
`:1628` (the branch). It is **not** consulted by `chunk_kda_householder` — that call
(`:1673-1682`) passes `q, k, v, g, beta, num_householder, cu_seqlens, backend` and no flag.

**`allow_neg_eigval` selects no kernel, no code path, and no different math.** It is purely a
multiply-by-two on a tensor, in eager PyTorch, before the kernel call, in both classes. The
in-tree test asserts exactly this and nothing more — `src/test/nn/attention/recurrent_test.py:1161-1174`
re-derives `beta = logits.sigmoid(); if allow_neg_eigval: beta = beta * 2.0` and checks the
realized ceiling is 1.0 vs 2.0.

The 22.1% cost is therefore attributable entirely to the *class*, not the *flag*. Everything
`KimiDeltaHouseholder` does differently is unrelated to negative eigenvalues:
- it calls its own hand-written kernel `chunk_kda_householder` (`:1605`, `:1673`) instead of fla's;
- it computes the gate eagerly in fp32 (`:1635-1638`) because "unlike `fla.ops.kda.chunk_kda` this
  kernel has no fused-gate path" (`:1631-1633`);
- it L2-normalizes eagerly (`:1669-1670`) because "The kernel has no `use_qk_l2norm_in_kernel`
  flag" (`:1667`);
- its backward allocates the `O(B·T·H·K·V)` fp32 state history that the class's own `.. warning::`
  at `:1434-1438` flags, which is the +2.54 GiB.

## 3. Any assert / clamp / range check on `beta` in fla-core 0.5.1's `chunk_kda` — CONFIRMED ABSENT, and the UT transform is unconditionally invertible

**No clamp, no range check, no upper bound.** The only `beta` assertion in `fla/ops/kda/chunk.py`
is a *shape* check (`:412`):

```python
    assert beta.shape == (B, T, HV), f"beta must have shape [B, T, HV]={[B, T, HV]}, got {list(beta.shape)}"
```

A sweep of every `beta` mention across all of `fla/ops/kda/` for `clamp|minimum|maximum` returns
only the two hits at `chunk.py:247` and `:255`, and both are about the **gate** `lower_bound`, not
beta. `fla/ops/utils/solve_tril.py` contains **zero** occurrences of `beta` — the inversion is
beta-unaware.

**The invertibility question is settled structurally, and beta cannot affect it.** The matrix
inverted is `I + A` where `A` is **strictly** lower triangular, so it is unit lower triangular:
determinant exactly 1, invertible for *any* finite entries, including `beta > 1`.

`fla/ops/utils/solve_tril.py:355-357` (public `solve_tril` docstring, verbatim):

```
    Compute the inverse of the matrix I + A
    A should be strictly lower triangular, i.e., A.triu() == 0.
```

The diagonal is zeroed *after* beta is applied, in both producers:

- `fla/ops/kda/chunk_intra_token_parallel.py:119` — `b_Akk = tl.sum(b_k * b_kgj, axis=1) * tl.where(j < i_t, 1.0, 0.0)`
  (strict `j < i_t`, so the `j == i_t` diagonal is exactly 0);
- `fla/ops/kda/chunk_intra.py:733,737,741` — `b_Akk = tl.dot(...) * b_beta[:, None]`, then
  `m_Akk = o_i[:, None] > o_i[None, :]` (strict `>`), then `b_Akk = tl.where(m_Akk, b_Akk, 0.0)`;
- and the identity is added back explicitly at `chunk_intra.py:289-294` (`b_Ai00 += m_I`, …) after
  forward substitution over the strictly-lower mask `m_A = o_i[:, None] > o_i[None, :]` (`:256`).

Beta scales only strictly-off-diagonal entries. It never touches the diagonal, so it can never
make the matrix singular at any value. The float64 reference `fla/ops/kda/naive.py:136` confirms
the same structure: `A = (A + torch.eye(BT, ...)) * beta[..., None, :]`.

The backward is likewise beta-magnitude-agnostic: `fla/ops/kda/chunk_bwd.py` uses `b_beta` only as
a multiplicative factor (`:254`, `:260`, `:277`, `:288`) — never a divisor, never a comparison.

**Contrast — our own Householder kernel DOES have a `beta == 1` singularity, and dodges it.**
`src/olmo_core/nn/attention/kda_householder.py:336-338`:

```
    The forward is *recomputed* rather than inverted: undoing a rank-1 delta update requires
    dividing by ``|k|^2 - 1/beta``, which is singular at ``beta == 1`` with L2-normalised keys --
    an interior point of ``beta = 2 * sigmoid(.) in (0, 2)``.
```

Note carefully: this is an argument for recomputation *instead of* inversion, and it is a hazard of
the **sequential** formulation. It bites at `beta == 1`, which is inside `(0,1)` too as a limit and
is reached in the strict regime as well. It is **not** a `beta <= 1` requirement, and fla's chunked
path does not invert the update at all — it inverts a unit-triangular matrix, which is safe.

## 4. Does fla itself expose `allow_neg_eigval` on a chunked op? — CONFIRMED YES, on `chunk_kda` directly

This is the finding that makes the work a config change.

`fla/ops/kda/chunk.py:189-190` (the public `chunk_kda` signature):

```python
    use_beta_sigmoid_in_kernel: bool = False,
    allow_neg_eigval: bool = False,
```

`fla/ops/kda/chunk.py:241-245` (its docstring, verbatim):

```
        allow_neg_eigval (bool):
            Whether to allow negative eigenvalues by scaling ``beta`` to ``[0, 2)``.
            Only takes effect together with ``use_beta_sigmoid_in_kernel=True``, in which case
            the kernel computes ``2 * sigmoid(beta)`` instead of ``sigmoid(beta)``.
            Default: ``False``.
```

And the implementation, `fla/ops/kda/chunk.py:61-62`:

```python
        if use_beta_sigmoid_in_kernel:
            beta = fused_beta_sigmoid(beta_raw, scale=2.0 if allow_neg_eigval else 1.0)
```

`fused_beta_sigmoid` is `fla/ops/common/gate.py:106`, and its kernel body is `b_y = scale *
tl.sigmoid(b_x)` (`:29`), with backward `b_dx = b_dy * scale * b_y * (1.0 - b_y)` (`:48`). **The
flag's entire effect inside fla is the scalar `scale`, 2.0 or 1.0, on a sigmoid.** Identical
semantics to our eager `beta * 2.0`.

Also confirmed on the sibling chunked ops: `fla/ops/gated_delta_rule/chunk.py:390-391, 273-274` and
`fla/ops/kda/fused_recurrent.py:252-253`. The only coupling constraint is a pairing requirement,
`chunk.py:400-401`:

```python
    if allow_neg_eigval and not use_beta_sigmoid_in_kernel:
        raise ValueError("`allow_neg_eigval=True` requires `use_beta_sigmoid_in_kernel=True`.")
```

**This does not bind us.** Our tree never passes `use_beta_sigmoid_in_kernel` (grep over `src/`
returns nothing), so it takes fla's default `False`, meaning we hand fla a **post-sigmoid** beta we
doubled ourselves. Both routes reach the same tensor; ours needs neither fla flag. The fused route
would be a marginal further optimization (one fused elementwise kernel instead of two eager ops),
not a requirement.

Two non-blockers worth recording: the `FlashKDA` backend refuses `use_beta_sigmoid_in_kernel=False`
(`fla/ops/kda/backends/flashkda.py:78-79`) — but it also refuses `torch.is_grad_enabled()` (`:65-66`),
so it is inference-only and irrelevant to training. And `chunk_gated_delta_product`
(`fla/ops/gated_delta_product/chunk.py:259-272`) exposes **no** `allow_neg_eigval` — the R>1 chunked
op is the one that lacks it, which is consistent with beta-doubling being expected at the layer.

## 5. Numerical stability at beta up to 2, argued honestly — the counterargument is real but does not survive contact with the evidence

The mechanism of concern is correct as stated: at `beta = 2` with `‖k‖ = 1` exactly,
`(I − beta·k·kᵀ)` has eigenvalue `−1` and is norm-**preserving**, so a product of `T` of them does
not contract. If bf16 rounding pushes `‖k‖² > 1`, then `|1 − 2‖k‖²| > 1` and the product can grow
geometrically. This is a genuine failure mode and deserved checking rather than dismissal.

**Evidence it is not realized, in five independent places:**

1. **Grazzi et al. (arXiv 2411.12537), §4.2 Eq. (4)** — the paper our own docstrings cite at
   `recurrent.py:657-658` and `:1454-1455` — defines `A⁻_GH(x) := I − 2φ(x)v(x)v(x)ᵀ` and states
   the norm bound directly: *"The norm of the matrix is still less than or equal to one, keeping
   the recurrence stable at long sequence lengths."* Its Table 2 gives the DeltaNet row as
   `I − βₜkₜkₜᵀ` → `I − **2**βₜkₜkₜᵀ`; Figure 11's diff is one line,
   `+ beta = 2 * rearrange(...).sigmoid()`. **§E.4 is decisive on the kernel question:** *"For
   DeltaNet, implementing the extended eigenvalue range is straightforward, since there is no need
   to modify the Triton kernel."* §5 claims *"no additional computational cost"*; Figure 7 reports
   *"All models trained stably with the same hyperparameters"* at 340M/1.3B over 100B tokens. Their
   stated caveats are for **diagonal** models (log-space cumprod incompatibility; degraded chunkwise
   GLA), not DeltaNet.
2. **DeltaProduct (arXiv 2502.10297)** — §5.1 *"we can reuse its implementation written in Triton …
   which uses the chunk-wise parallel form"*; §3 extends the range *"simply by multiplying βᵢ by
   2"*. Reports *"the training process remained stable"* (§5.3) and *"training behavior … is
   stable"* (§C.3.4). It has **no** numerical-precision appendix (checked v1 and v7: zero hits for
   fp32/bf16/numerical/instability). Its Table 2 trains and reports exactly our proposed cell,
   R=1 with negative eigenvalues ("DeltaNet[−1,1]").
3. **The chunked algorithm's own algebra** — DeltaNet (arXiv 2406.06484) Eq. (10),
   `T = (I + tril(diag(β)KKᵀ, −1))⁻¹ diag(β)`. The `−1` offset is the strictly-lower restriction,
   so `I + (strictly lower)` is unit triangular and unconditionally invertible. No condition on
   beta for existence or conditioning appears in the paper. This matches the 0.5.1 source read in
   Finding 3 exactly.
4. **Our own measured evidence, already in this tree.** `docs/dp2-kda/phase-0-1-runbook.md:351`
   records a decay/beta stress table comparing the Triton kernel against a float64 reference:

   | Regime | min exp(g) | max β | Triton vs float64, relative | finite |
   |---|---|---|---|---|
   | reflection beta (β ∈ (0,2)) | 2.25e-2 | **1.93** | 4.11e-3 – 5.39e-3 | yes |
   | baseline (logsigmoid gate) | 3.56e-2 | 0.98 | 3.53e-3 – 6.30e-3 | yes |

   The runbook's own reading (`:354`): *"All twelve cells finite, no NaN/Inf, and — the load-bearing
   observation — the three stress regimes land in the same 3.5e-3–6.3e-3 band as the baseline …
   `β_max = 1.93` confirms the reflection regime actually left the contraction range."*
5. **Our own production precedent.** Five 7B scripts under `src/scripts/official/OLMo-hybrid/` pass
   `allow_neg_eigval=True` explicitly (`OLMo-hybrid-7B-pretrain.py:78` and siblings) on
   `GatedDeltaNetConfig`, whose forward does the identical `beta * 2.0` (`recurrent.py:258-260`) and
   then calls the **chunked** `dispatch_chunk_gated_delta_rule` (`:284-286`). We already ship
   beta∈(0,2) through a chunked delta-rule kernel at 7B.

**The honest counterweights, stated rather than buried:**

- **RWKV-7 (arXiv 2503.14456) footnote 4** is the strongest instability report in the literature:
  *"we choose to allow only part of the range of possible negative eigenvalues in our pre-trained
  large language models due to experimentally observed training instabilities."* Caveat that cuts
  its force: RWKV-7's transition is an asymmetric DPLR matrix, a different kernel and a different
  spectral situation from a symmetric reflection with unit keys.
- **fla issue #537 ("solve_tril Numerical Explosion")** — maintainer `sustcsonglin`: *"In the delta
  rule, all elements in the lower triangular part are smaller than one, which is quite stable. …
  Without proper normalization, A remains invertible, but its condition number can be large,
  potentially leading to an inverse with large entries."* Note the premise "all elements < 1"
  presumes `β ≤ 1`, and `beta*2` breaks that premise. **Nobody asked him about the doubled case —
  that connection is our inference, not his claim.** Both #537 and #736 were resolved by enabling
  qk-norm, which we already do unconditionally (`use_qk_l2norm_in_kernel=True`,
  `recurrent.py:921`). Note also a real precision asymmetry: the fused BT=64 path sets
  `SOLVE_TRIL_DOT_PRECISION = 'tf32'` on cc ≥ 8 (`chunk_fwd.py:21`) while standalone `solve_tril`
  autotunes `'ieee'`, and `wy_fast.py:227` stores the inverse back at `k.dtype` (bf16). Escape
  hatch if ever needed: `FLA_TRIL_PRECISION`.
- **No published source reports NaN/divergence specifically from β∈(0,2) in a chunked bf16
  delta-rule kernel.** Across fla's GitHub there are 7 hits for `allow_neg_eigval`, all feature
  PRs — zero issues, zero discussions. PR #806 alleged bf16 inversion instability and was closed
  unmerged after the author conceded *"that's more of a hunch."* Absence of bug reports is weak
  evidence: the flag is off by default nearly everywhere and is likely under-exercised.
- **A real gap in our own coverage.** The in-tree R=1-vs-`chunk_kda` equivalence test
  (`src/test/nn/attention/kda_householder_test.py:315-347`) builds beta as
  `rnd(B, T * R, H).sigmoid()` (`:126`) — **never doubled**. So our numerical parity between the
  Householder kernel and `chunk_kda` is currently verified only for β∈(0,1). The runbook stress
  table (item 4 above) is what covers β up to 1.93, and it covers the Householder kernel against a
  float64 reference, not `chunk_kda`. Worth closing, and free to close.

**And the strongest honest caveat of all is about value, not stability:** two independent
1.3B-scale sources report that widening beta buys nothing on general LM. Grazzi Table 4 (FineWeb
100B, 1.3B, R=1): Wiki ppl 18.54 → 18.57, Avg 53.1 → 52.4, their words *"mixed results"*. GDN-2
(arXiv 2605.22791) Table 5: *"expanding the erase range from [0,1] to [0,2] gives no consistent
gain at this scale."* Where it *does* pay is state-tracking — DeltaProduct Table 2, R=1: Parity
0.233 → 0.982, average 0.263 → 0.726. So the right framing for the lead is not "free quality" but
**"free optionality on a state-tracking mechanism."** Our own `KDA_R1` CE (3.0749 vs `KDA_BASE`
3.0514, +0.0235) is consistent with "no CE gain" and is well inside the run's MDE of 0.0636
(`docs/mixer-bakeoff/HANDOFF.md:50-51`: *"no contrast clears the MDE — CE is NOT RESOLVED at n = 3"*).
`KDA_R1` also had the **worst sd of any arm, 0.04516**, ~4.4x `KDA_NOACT`'s.

## 6. The minimal change, and the cheapest experiment

**Minimal change: no new code. One argument in one factory.**

File `src/olmo_core/nn/transformer/core6_arms.py`, function `_kda` (`:170-172`), via the `MIXERS`
table at `:225-232`. Add one entry:

```python
    "kda_negeig": lambda: _kda(allow_neg_eigval=True),
```

and one `Core6Arm` naming `mixer="kda_negeig"`. That is the whole mechanism: `_kda` already
forwards `**kwargs` to `KimiDeltaAttentionConfig`, which already carries the field (`:1088`),
already forwards it to the layer (`:1397`), and the layer already implements the doubling
(`:874-876`) before calling `dispatch_chunk_kda`. **Zero lines of kernel work, zero lines in
`recurrent.py`.**

Parameter ledger: identical to `KDA_BASE` — the flag adds no parameters — so `ARM_L0_DELTA` takes
`K2_L0_DELTA`, exactly as `KDA_R1` and `KDA_NOACT` already do (`:148,150,152`).

**Cheapest experiment: a 3-cell incremental arm** on the frozen seeds 210007/220014/230021, paired
against the existing `KDA_BASE` cells. At $21.9576/node-hour, 0.5 h/cell, 1 node, **attempts=1**:

- 3 cells x 0.5 h x $21.9576 = **$32.94**
- Pin `attempts=1` explicitly. On profile defaults (`attempts:2`) the same arm compiles at
  **$65.87** — the declared-ceiling trap.

Two guards, because this arm is one where a null is the likely outcome and a vacuous null is worth
nothing:

1. **Assert the mechanism is live**, not just that the flag was set: log realized `beta.max()` per
   layer and require it `> 1.0`. A `2*sigmoid` whose logits all sit at −40 is
   indistinguishable from the strict arm. `recurrent_test.py:1176-1177` already has this assertion
   shape to copy.
2. **Assert throughput parity**, which is the actual claim: require `KDA_NEGEIG` tok/s within noise
   of `KDA_BASE`'s 419,288 and reserved memory equal to 10.721 GiB. If either moves, the "free"
   claim is false and we want to know from the receipt, not from a plausibility argument.

Cheap and worth bundling: extend `_make_inputs` in `kda_householder_test.py:126` with a
beta-doubled variant so the R=1-vs-`chunk_kda` parity test also covers β∈(0,2). That closes the
coverage gap named in Finding 5 on a GPU test we already run, at no marginal compute cost.

## DIRECT VERDICT

**Yes — the team can have negative eigenvalues at full KDA speed, and the capability is already
in the tree today with no kernel work required.** `allow_neg_eigval` is nothing but
`beta = beta * 2.0` in eager PyTorch in *both* classes (`recurrent.py:874-876` and `:1627-1629` are
character-identical), it selects no kernel and no branch, `KimiDeltaAttentionConfig` already carries
and forwards the field, and fla-core 0.5.1's chunked `chunk_kda` not only lacks any `beta ≤ 1`
assert, clamp, or invertibility assumption — the matrix it inverts is *unit* lower triangular, so
beta cannot make it singular at any value — but **exposes its own `allow_neg_eigval` on the chunked
op** whose entire implementation is `scale=2.0 if allow_neg_eigval else 1.0` on a fused sigmoid.
`KDA_R1`'s 0.779x and +2.54 GiB were paid for `KimiDeltaHouseholder`'s hand-written kernel — its
unfused gate, its eager L2-norm, and the `O(B·T·H·K·V)` fp32 backward workspace its own docstring
warns about at `:1434-1438` — not for the reflection regime, and the bake-off's own conclusion
already localized that cost to the kernel (`docs/mixer-bakeoff/HANDOFF.md:99`: *"kernel overhead
alone = 28.6%"*). The single next action: **add `"kda_negeig": lambda: _kda(allow_neg_eigval=True)`
to `MIXERS` in `src/olmo_core/nn/transformer/core6_arms.py:225-232` plus one `Core6Arm`, and run a
