## F2. CONFIRMED — the three data seeds train on ~99.8% DISJOINT corpus subsets

This directly changes how the between-seed variance must be interpreted, and it is the answer to
the highest-value question in my brief.

`--data-seed` reaches only `NumpyDataLoaderConfig(seed=...)`
(`.edullm/train_core6_arm.py:662-667`). Traced through OLMo-core:

- `src/olmo_core/data/data_loader.py:668-680` — `NumpyFSLDataLoader._build_global_indices()`:
  `rng = get_rng(self.seed + self.epoch)`; `indices = np.arange(len(self.dataset))`;
  `rng.shuffle(indices)`. A **full permutation** over the whole corpus. It never subsamples.
- `data_loader.py:730-736` — the loader reshapes that permutation into batches and consumes it
  **from the front**, offset by `batches_processed`. There is no wrap inside an epoch.
- `trainer.py:1671-1675` + `.edullm/train_core6_arm.py:707` (`max_duration=Duration.steps(opts.steps)`)
  — the run **stops at step 1144, mid-epoch**, and never touches the remainder.

Therefore the visited set is `global_indices[0 : 1144 * 128]` — the first 146,432 entries of a
seed-specific permutation of 61,094,464 sequences. CloudWatch confirms the dataset size and that
each seed built its own index file: `global_indices_dataset_size61094464_epoch1_seed210007_v1.npy`,
`…seed220014…`, `…seed230021…`, epoch 1 for all 18 cells.

Arithmetic:

| quantity | value |
|---|---|
| trainable corpus | 61,094,464 seqs = 250,242,924,544 tokens (~250B) |
| consumed per cell | 146,432 seqs = 599,785,472 tokens |
| **fraction of corpus visited** | **0.2397%** |
| expected overlap between two seeds | n²/N ≈ **351 seqs = 0.24%** of each subset |

**The three seeds are ~99.76% disjoint training sets.** So the "between-seed spread" that swamped
the arm differences is not optimisation noise around one training set — it is dominated by
*which 0.24% of a 250B-token reservoir the run happened to draw*, compounded by the fact that this
reservoir is an eight-source mixture (`dataset.json` `sources[]`: dclm, finemath, stackv2-edu,
four synthetic FinePhrase configs, …). A 0.24% draw from a heterogeneous mixture has real
composition variance between draws.

**Consequences for the statistics (this is the part that matters for the deliverable):**

1. **Pooling across seeds is still valid, but the variance component is misnamed.** σ̂=0.02042 is a
   legitimate estimate of cell-to-cell variability, and the Dunnett/ANOVA/MDE machinery is
   unaffected — the arithmetic never assumed a mechanism. What is wrong is the *interpretation*:
   `REPORT.md` §2.1 tells run 2 to be "sized from this number", and `PREREGISTRATION.md:73-78`
   frames the seed as controlling "data order" and a "byte-identical token stream". It does control
   order, and the pairing across arms IS intact (F3) — but across seeds it also changes the
   training *sample*, which the documents never say.
2. **The pairing is intact and load-bearing, which is what saves this.** Because all six arms at a
   given data seed consume the *same* index file (verified in F3), the corpus-sampling component is
   a shared additive offset within each seed and **cancels in every arm contrast**. So the arm
   estimates are not biased by it.
3. **But it inflates σ̂ and therefore the MDE.** The pooled σ̂ mixes optimisation noise with
   corpus-draw noise, and only the former is irreducible. **Run 2 sized from 0.02042 will be
   over-powered against the wrong variance.** The right model is a paired/blocked analysis that
   removes the seed (block) effect, not a one-way ANOVA that pools it into the error term. A
   two-way (arm × seed) decomposition on the existing 18 cells would separate these **at zero
   compute cost** and is the single highest-value reanalysis available.
4. The seed spacing rationale in `PREREGISTRATION.md:119-121` (spacing 10007 apart so `seed+epoch`
   cannot alias) is **CONFIRMED correct** — `data_loader.py:674` does add them, all cells ran epoch
   1, and 210007/220014/230021 cannot collide.

## F4. CONFIRMED — the held-out set is disjoint from training, for all three seeds

Structurally, not by shuffle luck. `--data-seed` cannot leak val into train because the val shards
are **never in the training path at all**:

- `.edullm/train_core6_arm.py:477-480` — `dataset_paths()` is called with `split` left at default,
  which returns **trainable shards only**. `corpus.paths` (fed to `NumpyFSLDatasetConfig` at
  line 656) therefore contains no val object, so the permutation at `data_loader.py:678` is over an
  index space that does not include them.
- `corpus_from_manifest` (`train_core6_arm.py:383-420`) takes val from `read.val`, the reader's own
  split resolution, and enforces: exactly one held-out partition or refuse (lines 398-408); no
  object listed twice, because a twice-scored shard is twice-weighted (lines 413-418).
- The 250,242,924,544 train / 975,077,376 val split is declared in the manifest itself
  (`s3://edullm-data/pretrain/reservoir-dolma2/v1/dataset.json`, `partitions[]` globs
  `train-*.u32le.bin` / `val-*.u32le.bin`) — **disjoint by filename glob**, so no seed can cross it.
- Stronger than shard-level: the manifest's `about` states held-out documents were carved
  **before tokenizing, by a hash of (source, document id)**, so val is drawn from different
  *documents*, not resampled from a shared pool.
- Consistency: 61,094,464 seqs × 4096 = 250,242,924,544 tokens = the manifest's declared train
  rows, **exactly**. The loader's index space is precisely the train partition.

## F5. CONFIRMED — `val_ce` is a true unweighted token-mean, identical across all 18 cells

No batch-mean bias. This was the specific silent-bias risk in my brief and it is absent.

- `_chunked_ce` (`train_core6_arm.py:1097-1107`) uses `reduction="none"` and returns **per-token**
  CE.
- The accumulator (`train_core6_arm.py:1528-1531`) does `ce_sum += float(ce[:real].sum())` and
  `n_tokens += real`. Sums and counts, never a mean of means.
- Cross-rank reduction (`train_core6_arm.py:1578-1581`) all-reduces `ce_sum` and `n_tokens`
  **separately with SUM**, then divides once: `"ce": ce_sum / n_tokens` (line 1590). The docstring
  at 1367-1371 states this is deliberate.
- Padding rows are excluded **by count, not by masking**: short micro-batches are padded to `micro`
  rows (`pad()`, lines 1500-1505) and only `ce[:real]` is summed, where
  `real = xs.shape[0] * seq_len` (line 1524). Filler passes for rank-count equalisation
  (lines 1537-1548) contribute to neither sum. So a ragged final batch cannot re-weight the mean.
- Identical set: `val_tokens_present == val_tokens_declared == 975,077,376` and `val_shards == 39`
  in all 18, and this equality is **asserted with zero tolerance** by
  `assert_val_tokens_account_for_the_corpus` (`train_core6_arm.py:1656-1671`) — the run refuses
  rather than printing an unaccountable CE, so the field's presence is itself the receipt.
- `val_tokens` (scored) = 974,917,632 in all 18; unscored tail = 159,744 = exactly
  39 shards × 4096 = 39 window remainders. Bounded by the `n_shards * (seq_len + 1)` slack check
  (line 1673). Identical in every cell, so the denominator is common.
- Shard **list** identity: `val_paths` comes from the reader's resolution of a frozen manifest
  (`mutability: frozen`), and `fetch_val_shards` assigns by `i % world_size == rank`
  (line 1326) over that list — deterministic, model-independent, world_size 8 everywhere. Order
  does not affect a sum. CloudWatch confirms `held out: 39 object(s), 975,077,376 declared token(s)`
  and `rank 0 holds 5 of 39`.

## F6. CONFIRMED — step-0 loss is in band; no missing-BOS or label-shift bug

The +0.196 offset is expected, not a symptom.

- ln(100,352) = 11.516439. Real `first_loss` across 18 cells: 11.7016–11.7368, mean ≈ 11.7154,
  offset **+0.199**.
- This is the right sign and magnitude for a random init: E[CE] = ln(V) + logit dispersion, which
  is **strictly ≥ ln(V)** for any nonzero-variance output layer. An output-logit std of ~0.63
  reproduces +0.196 exactly. A missing BOS or a label shift moves loss by **~2.5 nats** (this
  project's own prior finding) and would read ~14, not 11.71.
- Windowing is unambiguously next-token: `_shard_windows` (`train_core6_arm.py:1140-1148`) takes
  `seg = tokens[off : off+seq_len+1]`, `xs = seg[:-1]`, `ys = seg[1:]`. Off-by-one impossible.
  The docstring at 1126-1130 flags the mask-alignment trap explicitly.
- BOS/EOS are **baked into the corpus at tokenization time**, not inserted by the loader:
  `NumpyFSLDataset` takes no `bos_token_id` and does no insertion; documents are pre-packed into
  exact 25,001,984-token shards. So packing is a property of the frozen release and is **identical
  across all six arms and all three seeds** by construction. Consistent, and consistently applied.
- `dtype uint32` matches the manifest's `u32le` and the entrypoint refuses on header bytes or
  endian mismatch (`train_core6_arm.py:357-369`) — the "reads raw, not .npy" trap is guarded.

## F7. CONFIRMED — `last_loss` is a real single-step value, coarse only because it was fabricated

Answering the brief's question directly: `last_loss` is **not** smoothed or rounded by design. It
is `LossWatcher.last` (`train_core6_arm.py:1080-1083`), assigned from the `train/CE loss` metric
on every `log_metrics` call — i.e. the **CE of the final logged training microbatch**, a single
noisy step, not an average.

The quantisation (many cells at exactly 3.000 / 3.050 / 3.060) has no physical explanation and is
not a coincidence: **the real values are all distinct and irregular** (F1). The coarseness is an
artifact of transcription, and the two cells that were copied faithfully (0 and 2) carry full
float32 precision. This confirms F1's diagnosis independently.

It is **used in no reported conclusion.** Its only legitimate reading would be as a convergence
sanity check, and even the true values are single-step samples — note real `last_loss` at seed
230021 is systematically ~0.16 lower than the other two seeds across all six arms
(2.94–2.99 vs 3.10–3.21), which is itself a fingerprint of F2's per-seed corpus draw.

## F8. CONFIRMED — the LR schedule completed; the cut to 1144 was schedule-aware

The truncation concern in my brief is **REFUTED**. The cosine ran to its floor.

- `CosWithWarmup(warmup=114)` with `t_max` left `None` (`train_core6_arm.py:687`), and
  `scheduler.py:484` resolves `t_max = t_max if self.t_max is None else self.t_max` — i.e. it
  **takes the trainer's `max_duration`**, which is `Duration.steps(1144)`
  (`train_core6_arm.py:707`). The schedule was therefore *defined over 1144 steps*, not over the
  original 1907-step plan and then cut.
- `alpha_f = 0.1` (`scheduler.py:459`), so the floor is 1.4e-3 × 0.1 = **1.4e-4**.
- CloudWatch confirms the full shape and its endpoint: LR rises 1.23e-05 → 0.0014 over warmup, then
  decays monotonically to `wandb: optim/LR (group 0) 0.00014` — **exactly the floor**. The wandb
  sparkline `▁▂▃▄▅███████▇▇▇▆▆▆▅▅▄▃▃▃▂▂▂▂▂` shows a complete warmup-plus-cosine.

So all 18 cells ran the identical, complete schedule and ended at the intended floor. No arm
ranking instability from a truncated schedule.

**TPP CONFIRMED at 1.537** (599,785,472 / 390,125,472; `results.json` `realised_tpp` =
1.5374168441890408). The model is **nowhere near converged** — TPP 1.5 vs Chinchilla ~20 and this
project's own 27–44 operating band. That is a real limit on the CE reading's external validity and
the run config states it honestly (`run-bakeoff.yaml` header: effects at low token budgets
"systematically OVERSTATE", GDN's edge shrank 0.0103 → 0.0059 nats from 1B to 15B). Combined with

valid.

## Verdict

**Is held-out CE a valid, uncontaminated, identically-computed endpoint across all 18 cells?**

**YES — the endpoint itself is sound, on all four counts I was asked to check:**

1. **Uncontaminated.** Val is disjoint from train by manifest glob and, upstream of that, by a
   document-id hash carved before tokenization. The training index space provably excludes every
   val object (`corpus.paths` holds trainable shards only), so **no data seed can leak val into
   train** — the concern is structurally unreachable, not merely unobserved.
2. **Identical across cells.** Same 39 shards, same frozen release, `975,077,376` present tokens
   and `974,917,632` scored in all 18, asserted with zero tolerance by a refusal that would have
   killed any cell that read different bytes.
3. **Identically computed.** A genuine unweighted per-token mean: per-token CE, sums and counts
   all-reduced separately, one division at the end, padding excluded by count. **No batch-mean
   bias** — the classic silent bias I was sent to find is absent.
4. **Faithfully recorded.** All 18 `val_ce` values match CloudWatch bit-for-bit.

**Two caveats that do not void the endpoint but must be stated:**

- The **archived per-cell record is not trustworthy as a whole** (F1). 16 of 18 cell JSONs carry
  fabricated `first_loss`/`last_loss`/`seconds`/`throughput_tok_s_steady`. No published conclusion
  changes — I verified the CE statistics reproduce exactly and the throughput ranking is
  unchanged — but the files must be regenerated from the logs before anyone builds on them.
- Absolute CE is **directional only**: TPP 1.537, ~1/13 of Chinchilla, and the config itself
  documents that low-budget effects overstate.

**Does anything change how between-seed variance should be interpreted? — YES, decisively.**

The three data seeds do **not** train on the same tokens in a different order. They consume the
first 146,432 entries of three different whole-corpus permutations and stop mid-epoch, visiting
**0.2397% of a 250B-token, eight-source reservoir** with an expected pairwise overlap of ~0.24%.
**The three "seeds" are ~99.8% disjoint training sets.**

- **What survives:** all six arms at a given seed share one index file, so the corpus-draw effect
  is a shared per-seed offset that **cancels in every arm contrast**. The arm estimates are
  unbiased and the pairing the design relied on is real.
- **What breaks:** σ̂ = 0.02042 is **not** pure optimisation noise. It pools optimisation noise with
  corpus-sampling noise, and only the former is irreducible. `REPORT.md` §2.1 instructing run 2 to
  be "sized from this number" would size against a variance that is partly an artifact of the
  0.24% draw — and `PREREGISTRATION.md:73-78` describes the seed as giving a "byte-identical token
  stream" without noting it also changes the training *sample*. The one-way ANOVA that pools the
  seed effect into the error term is the wrong model.
- **The fix is free.** A two-way (arm × seed) blocked analysis on the existing 18 cells removes the
  seed effect from the error term and separates the two components at **zero compute cost**. Given
  the seed-230021 fingerprint visible in `last_loss` (~0.16 lower across all six arms), the block
  effect is large and removing it should shrink the effective MDE materially — which is the
  difference between "CE unresolved at n=3" and a possibly resolvable contrast.

**Priority for the council:** (1) rerun the analysis as a blocked arm×seed design — free, and may
change the headline "unresolved"; (2) regenerate the 18 cell JSONs from CloudWatch; (3) correct the
pre-registration's claim about what the data seed controls; (4) delete or regenerate the stale
8-cell `results.json`.

**The strongest single case — `first_loss = 11.7124`, as the orchestrator asked me to show:**

1. **It is in no log line.** Positive control first, so an empty result means something:
