## FINDING 2: Non-endpoint fields are corrupted/transcribed in 16 of 18 committed files — CONFIRMED

Only **cell-0.json and cell-2.json are verbatim across every field.** The other 16 (idx
1, 3–17) show a consistent, non-random corruption pattern confined to four fields:

**(a) `first_loss` — fixed placeholder, not per-cell data.** The committed value is the exact
literal `11.7124` in all 16 corrupted cells. The genuine log values range 11.6959–11.7368 across
cells (spread ≈0.04) and never equal 11.7124 in even one of the 16 (closest: idx4 at
11.712780952453613, which still isn't 11.7124 exactly). This is a flat placeholder, not a
rounding of real per-cell data.

**(b) `last_loss` — wrong, and not a plausible rounding of the genuine value.** E.g. idx9
committed 3.05 vs log 3.153482437133789 (off 0.10); idx13 committed 3.08 vs log
3.2073452472686768 (off 0.13); idx14 committed 3.05 vs log 2.9415836334228516 — the committed
value is *higher* than the true last loss. idx17 committed 3.06 vs log 2.948591709136963 (off
0.11, wrong direction). These are not a truncated/rounded version of the real number; they look
hand-typed to a plausible round figure.

**(c) `seconds` — usually a plausible-but-wrong round number.** Several cells round correctly
(idx7, 10, 11, 12, 13, 14, 15, 17 round to the true value within ≤1s), but several do not: idx3
committed 1844 vs true 1827.37 (off 17s), idx6 committed 1846 vs true 1845.53 (rounds fine), idx8
committed 1850 vs true 1844.70 (off 5s), idx9 committed 1843 vs true 1821.90 (off 21s), idx16
committed 2230 vs true 2226.01 (off 4s). Mixed — some right, some off by double digits of
seconds.

### 2a. This directly explains a peer's bit-exactness finding

The relationship `throughput_tok_s_steady_per_device * 8 == throughput_tok_s_steady` holds
bit-exactly in the genuine logs (confirmed on idx0, idx2 explicitly; true by construction
elsewhere), but breaks in committed files wherever `_steady` was substituted from the all_steps
family while `_per_device` was independently rounded from the genuine steady value (or vice
versa) — this is the mechanism behind the "holds in only 5/18" observation.

### 2b. Not caused by the Dynamo recompile issue (Finding 3)

Cells 3–8 (KDA_NOACT, KDA_GCONV) are **completely clean of recompile_limit events** (Finding 3)
yet still show the `first_loss`/`last_loss` placeholder corruption in 5 of those 6 cells (all but
idx0/idx2, which are BASE, not NOACT/GCONV — to be precise: idx3–8 are ALL corrupted on
first_loss/last_loss despite being recompile-clean). Cells 9–17 (recompile-affected) show the
same corruption pattern. **The two phenomena are independent bugs**, not cause-and-effect.

### 2c. Material-impact check: does this corruption change REPORT.md's conclusions? CONFIRMED — no.

REPORT.md §3's per-arm throughput means were traced back to the **committed** (corrupted)
`throughput_tok_s_steady` values, not to genuine log values — e.g. its GCONV mean of 410,690

The bias introduced by the corruption is two to three **orders of magnitude smaller** than the

## FINDING 4: KDA_GCONV fused-conv path — UNSUPPORTED / inconclusive from logs alone

Grepped idx6–8 (the only KDA_GCONV cells) for `causal_conv1d`, `use_fla`, `falling back`,
`fla.ops`, `ImportError`, `nn.Conv1d`, `ShortConv`, `fused`, `gated_conv`. All three cells print
an identical config dump:

```
sequence_mixer=ShortConvConfig(kernel_size=3, gate_structure='dense', gate_rank=None,
gate_groups=None, bias=False, use_fla=True, dtype='float32')
```

`use_fla=True` was the **configured** value for all three cells. No `ImportError` or explicit
fallback message appears anywhere in the matched lines. However, per this project's own prior
finding (`fla-optional-fast-path-biases-baseline` — "short_conv.py defaults use_fla=True but fla
is absent, so the static arm silently runs nn.Conv1d") a fallback of this kind is known to leave
**no log signature at all** in this codebase. Config-value confirmation is therefore necessary
but not sufficient. **I cannot confirm from CloudWatch logs alone whether the fused FLA kernel
was actually exercised at runtime versus a silent eager fallback for cells 6–8.** Labeled
UNSUPPORTED, not REFUTED or CONFIRMED either way.

## Bottom line

The 18 committed JSONs are **faithful on everything load-bearing for the recommendation** —
`val_ce`, `parameters`, `peak_memory_gib`, and every provenance fact are exact matches to AWS
CloudWatch and Batch, cross-checked against the actual submitted command three independent ways.
They are **not faithful as a verbatim transcription** — 16 of 18 files show a first_loss
placeholder, a wrong last_loss, and (mostly) a substituted throughput field, most likely produced
by a script or hand-entry process that read the wrong keys out of the same summarize() JSON
rather than by data corruption on AWS's side. This is a real defect that should be fixed by
regenerating the 16 affected files from source, but it does **not** change REPORT.md's
recommendation of `KDA_BASE`, because the primary endpoint it actually decides on (CE, and
secondarily throughput/memory) was untouched or only negligibly touched by the bug.
