## 2. Is `KDA_R1` the same function as `KDA_BASE`? — **REFUTED as written**

### Differences that are exact/algebraic no-ops at R=1 (arithmetic-only)
1. **Gate computation site.** KDA hands the *raw* pre-activation gate to fla's fused kernel
   (`use_gate_in_kernel=True`, `recurrent.py:917-926`), which computes
   `-exp(A_log)*softplus(raw+dt_bias)` internally. Householder computes it eagerly in **float32**
   (`recurrent.py:1632-1636`). Algebraically identical, different rounding.
2. **q/k L2 normalisation site.** KDA uses `use_qk_l2norm_in_kernel=True` (`:922`); Householder
   calls `l2_normalize` eagerly (`:1668-1670`). The comment at `:1667` notes this matches KDA's
   post-convolution ordering.
3. **Kernel identity.** KDA -> `dispatch_chunk_kda` -> `fla.ops.kda.chunk_kda`
   (`flash_linear_attn_api.py:45,99-100`), a **chunked** kernel. Householder ->
   `chunk_kda_householder`, which despite the name is a **sequential fused-recurrent** Triton
   kernel (`kda_householder.py:697-699`). Same `scale = K**-0.5` default
   (`kda_householder.py:786`; `flash_linear_attn_api.py:77`).
4. **Reshape/interleave plumbing** — degenerate at R=1 (`T*R == T`).
5. **Conv init helper.** KDA uses `_init_short_conv` (`recurrent.py:983`), Householder uses
   `init_linear` (`recurrent.py:1745`). For a **plain** `CausalConv1d` these are the same call:
   `_init_short_conv` dispatches on type and calls `init_linear(conv, ...)` for `nn.Conv1d`
   (`recurrent.py:98-99`), and `CausalConv1d` **is** an `nn.Conv1d` (`convolution.py:12`).
   Equivalent for `KDA_BASE`/`KDA_R1`. Same `A_log = log(U(1,16))`, `dt_bias = 0` in both
   (`:984-986` / `:1747-1749`). Same conv activation (silu) — KDA from config default
   `conv_activation="silu"`, Householder hardcoded `ActivationFunction.silu.value`
   (`:1537,1545,1553`). Same `o_norm` = `FusedRMSNormGated(activation="sigmoid")`
   (`:770` / `:1568`). Same param shapes at R=1.

**Verified by the repo itself:** `recurrent_test.py:1049-1131`
(`test_kimi_delta_householder_r1_copied_weight_module_parity`) copies weights via
`load_state_dict(strict=True)` and asserts output + gradient parity to a bf16 budget (2e-2 / 5e-2).
So *at equal `allow_neg_eigval`* the two are the same function up to fused-vs-eager rounding.
**But that test constructs both with the default `allow_neg_eigval=False`**
(`:1077-1082` pass only `n_heads/head_dim/expand_v`). It therefore validates
`R1(False) == KDA(False)` — **not** the configuration that ran.

### The difference that is NOT a no-op
6. **beta range.** `KDA_BASE`: `beta ∈ (0,1)`, contraction. `KDA_R1`: `beta ∈ (0,2)`, admits true
   reflection. This is a **different operator with a different reachable state-transition set**, not
   a rounding difference.

The repo says so in the immediately following test,
`recurrent_test.py:1134-1181` `test_kimi_delta_householder_strict_beta_contract`: *"the strict and
reflection beta regimes cannot be conflated ... These are separate arms: the runbook forbids
pooling them, because at `beta = 2` with unit keys the composed erase multiplier returns to `+1`
and the update degenerates rather than vanishing, so a reflection result is not an extrapolation
of a strict one."* And `:1175-1178` asserts the two regimes must be "genuinely distinguishable,
not merely differently labelled."

**Verdict.** At R=1 *with `allow_neg_eigval` equal*, yes — same function (rounding aside), and
the repo has a GPU test proving it. **As actually configured, no.** The HANDOFF's "and the same
function" (`HANDOFF.md:98`) is **false for the pair that ran**. The arm registry
(`core6_arms.py:442-450`) is the accurate description: `KDA_R1 − KDA_BASE` is "the beta-in-(0,2)
reflection regime ALONE." The HANDOFF and the registry **contradict each other**, and the
registry is right.

## 3. How much of the gap is attributable to what — **the throughput split SURVIVES; the CE/variance use does NOT**

This is the key distinction, and the two uses come apart cleanly.

### (a) Throughput decomposition — SURVIVES (with a caveat on the estimator)
`beta * 2.0` is one elementwise multiply on a `[B,T,R,H]` tensor — at H=16, R=1 that is 16 values
per token against a 2.47e9 FLOP/token layer. Measured `flops_per_token` is **bit-identical**
between `KDA_BASE` and `KDA_R1` (both `2,473,388,544`; cell JSONs), so the FLOP accounting does
not even see it. It cannot plausibly produce 22%. The 22% is real and is a property of the
**code path** (sequential fused-recurrent vs chunked, plus eager fp32 gate/l2norm), which is what
"kernel" means here.

Also independent of the beta regime: **reserved memory** 13.260 vs 10.721 GiB (+23.7%), the
`O(B*T*H*K*V)` fp32 backward workspace documented at `kda_householder.py:702-706`. This is
allocated by the kernel regardless of beta. **The memory case for the 4–7 day chunking rewrite is
untouched by this concern** and is the stronger case, as the HANDOFF itself says
(`HANDOFF.md:236-240`).

Caveat: strictly, the R1-vs-BASE speed gap bundles *kernel* with *the eager fp32 gate+l2norm* —
both are "implementation, not mechanism," so the headline survives, but "kernel overhead" is
loosely named.

### (b) CE / quality decomposition — DOES NOT SURVIVE
`KDA_R1` is used at `HANDOFF.md:88-103` as the control that makes "the Householder result
interpretable," i.e. as the term that isolates arity in `KDA_R2 − KDA_R1`. For CE that requires
R1 and BASE to differ only in implementation. They do not — they differ in the beta regime, a
real mechanism. So:
- `KDA_R1 − KDA_BASE` on CE (+0.0236 nats) = **reflection regime + implementation rounding**,
  confounded, not attributable.
- `KDA_R2 − KDA_R1` on CE is **still clean for arity** (both are `allow_neg_eigval=True`,
  same kernel, same class) — this contrast is *unharmed*, and is in fact the only reason R1 has
  scientific value on the CE axis. **A3-style framing note: R1's value as an arity control is
  intact; its value as a "same function" kernel control is not.**
- There is also a **param/FLOP asymmetry against R2** that is separate from this concern:
  `KDA_R2` has `flops_per_token = 2,457,037,312` — **0.66% BELOW** `KDA_BASE`/`KDA_R1`'s
  `2,473,388,544` — and `parameters = 390,141,856` vs `390,125,472`, because `solve_widths`
  respends the mixer surplus out of FFN width (`core6_arms.py:538-555`). So `KDA_R2 − KDA_R1` is
  param-matched-to-tolerance but **not** FLOP-identical. The HANDOFF's "(2,473,388,544 FLOP/token,
  verified equal)" is true of R1-vs-BASE only.

## 5. The `backend="torch"` cheap check — CANNOT distinguish kernel from mechanism as proposed

`backend` **exists** and is genuine: `KimiDeltaHouseholderConfig.backend: Literal["triton","torch"]
= "triton"` (`recurrent.py:1851-1861`), forwarded at `:1966`, stored and passed to the kernel at
`recurrent.py:1673`, dispatched at `kda_householder.py:730-732,785`. `"torch"` is a pure-PyTorch
Python loop over T and R (`kda_householder.py:686-699`, `kda_householder_torch.py:7,28`).

**It cannot separate kernel from mechanism**, for two reasons:
1. Both backends keep `allow_neg_eigval=True`, so **the beta regime is held fixed at the wrong
   value** — the confound is present in both arms of the proposed comparison. It varies only the
   implementation, so a persisting spread rules out *rounding order* but says nothing about
   whether the reflection regime is the cause. The HANDOFF's own inference — "If the spread
   persists, it is not the kernel" (`HANDOFF.md:246-247`) — is valid only against candidate (2)
   and silently omits candidates (1) and (3), which it cannot address.
2. **It is not cheap.** The torch backend is documented as **~400x slower** than Triton at
   B2/T8192/R4 (`kda_householder.py:78-79`). R1 cells ran at `step_time_s_p50 ≈ 1.58 s` x 1,144
   steps ≈ 30 min/cell; at even 100x that is weeks of A100 time per cell. It is a **CPU/float64
   `gradcheck` reference**, not a training backend. Proposing it as the "cheap check" misprices it
   by orders of magnitude.

## 6. Arithmetic — the 28.6%/10.9% pair is INCONSISTENT (mixed estimators); A3's ~28.4% is right

`1/0.779 − 1 = 28.37%`, and `1 − 0.779 = 22.13%`. From raw cell data (mean of 3):

| basis | overhead BASE->R1 (time) | throughput loss | arity R1->R2 (time) |
|---|---|---|---|
| `throughput_tok_s_steady` (n=3) | **28.414%** | 22.127% | **10.443%** |
| `tps_device_avg` / `all_steps` | 28.442% | 22.144% | 10.443% |
| mean `step_time_s_p50` | 28.374% | — | 11.584% |
| **`step_time_s_p50`, seed 210007 only** | **28.577% -> "28.6"** | — | **10.942% -> "10.9"** |
| `throughput_tok_s_whole_run` | 9.751% | 8.885% | 10.737% |

**Findings:**
- **"Overhead" as a time/cost multiplier is the correct framing** — `1/ratio − 1`, i.e. "R1 takes
  28.4% more time per token." `1 − 0.779 = 22.1%` is the *throughput loss*, a different and
  smaller quantity (same fact, different denominator). The HANDOFF's choice of framing is right;
  the two must simply never be mixed, and the label should say which it is.
- **A3 is correct and the HANDOFF is not.** On the n=3 steady-state means that produced the
  published `0.779x`, the figures are **28.41%** and **10.44%**. **28.6% / 10.9% are both from a
  single cell (seed 210007) on `step_time_s_p50`** — I reproduced them to 3 significant figures
  (28.577%, 10.942%) and no n=3 estimator yields that pair. So the headline decomposition is an
  **n=1 reading presented as the run's result**, mixed with an n=3 `0.779x` in the same sentence.
- **Internal consistency check:** the two steps must compose to the measured total.
  `1.28414 x 1.10443 = 1.41824` = measured `BASE/R2` time ratio `1.41825`. Exact.
  The published pair gives `1.286 x 1.109 = 1.42617` — **off by 0.8pp**, the signature of the
  mixed estimator.
- Note also `throughput_tok_s_whole_run` gives 9.75%, not 28.4%, because it includes startup —
  consistent with the project's "measure throughput post-startup" rule; the steady-state basis is
  the right one and the HANDOFF used it for `0.779x`.

**Correct statement:** kernel+eager-gate overhead = **28.4%** (time), arity step = **10.4%**,
composing to the measured **41.8%** total. Or in throughput terms, 22.1% and 9.5%.

## Verdict

**The "kernel, not mechanism" conclusion is NOT valid as written, but it fails in a narrower way
than a reader of the concern might expect — and the two things the claim is used for come apart.**
The factual premise is confirmed: `KDA_R1` ran with `allow_neg_eigval=True` (`core6_arms.py:192`)
and `KDA_BASE` with `False` (`recurrent.py:1088`), the repo's own test asserts this
(`core6_arms_test.py:233-234`), and the repo's own test says the two beta regimes "cannot be
conflated" (`recurrent_test.py:1138-1142`). So **"and the same function" (`HANDOFF.md:98`) is
false**, and the arm registry (`core6_arms.py:442-450`, "the beta-in-(0,2) reflection regime
ALONE") contradicts the HANDOFF and is the correct description. **However, the throughput
decomposition survives on physics**: `beta*2.0` is one elementwise multiply, measured
`flops_per_token` is bit-identical between the two arms, and the +23.7% reserved-memory gap is a
documented fp32 backward workspace — so the speed/memory case for the 4–7 engineer-day chunking
rewrite stands, and stands *primarily on memory*, which the HANDOFF already says is the stronger
case. **What does not survive is every use of R1 as a quality/variance control**: the CE delta
`R1 − BASE` (+0.0236 nats) is confounded, "17x the best arm on mathematically identical
computation" is false on its own terms, and "suspected kernel-induced instability" is contradicted
by `KDA_R2` sharing that kernel at sd 0.00642 while a mechanism explanation the HANDOFF cannot
see — a single un-composed reflection at R=1 — is at least as plausible. The strongest TRUE
statement the data supports: *"`KDA_R1` is the Householder class at R=1 in the beta∈(0,2)
reflection regime; it is parameter- and FLOP-identical to `KDA_BASE` but differs from it in both
implementation and beta range. Its 28.4% time overhead and +23.7% reserved memory are safely
attributable to implementation, because the beta regime is one elementwise multiply and costs no
FLOPs. Its CE and its variance are NOT attributable, because implementation and mechanism moved
together. The arity contrast `KDA_R2 − KDA_R1` remains clean on both axes."*
**Required changes to the deliverable:** (1) delete "and the same function" and state the
`allow_neg_eigval` difference explicitly wherever R1 and BASE are compared; (2) restate the
decomposition as **28.4% / 10.4%** from n=3 steady-state, and note that these compose to the
measured 41.8% — the published 28.6%/10.9% is a single-cell reading that does not; (3) confine
the "kernel" attribution to throughput and memory, and retract it for CE and for the sd claim;
(4) mark the variance excess UNRESOLVED with the 2x2 showing both single-factor explanations
failing, and disclose that R1 supplies 81.6% of the pooled SS so that σ̂=0.02042/MDE=0.0636 would
be 0.00961/~0.0299 without it — while noting no outlier rule was pre-registered, so R1 stays in;
(5) replace the `backend="torch"` "cheap check" with the `KDA_R1_STRICT` arm (3 cells, or 6 with
`KDA_BASE_NEG`), since the torch backend holds the confound fixed and is ~400x slower, not cheap;
