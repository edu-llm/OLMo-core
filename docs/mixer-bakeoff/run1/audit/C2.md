## HEADLINE (answers task item 2)

**CONFIRMED — REFUTED that the Householder class is needed for negative eigenvalues.**

`beta in (0,2)` is a **beta-projection change, not a kernel change**, and the fast chunked
`chunk_kda` already implements it as a first-class, named, shipped argument.

1. `chunk_kda` takes `allow_neg_eigval: bool = False` in its public signature —
   `/private/tmp/flasrc/c051/fla/ops/kda/chunk.py:190`.
2. Its docstring states the semantics exactly: *"Whether to allow negative eigenvalues by
   scaling `beta` to `[0, 2)`. Only takes effect together with `use_beta_sigmoid_in_kernel=True`,
   in which case the kernel computes `2 * sigmoid(beta)` instead of `sigmoid(beta)`."* —
   `fla/ops/kda/chunk.py:241-245`.
3. The **entire** implementation is one scale factor on the sigmoid:
   `fla/ops/kda/chunk.py:62` → `beta = fused_beta_sigmoid(beta_raw, scale=2.0 if allow_neg_eigval else 1.0)`
   and its backward twin `fla/ops/kda/chunk.py:170` →
   `db = fused_beta_sigmoid_bwd(beta_raw, db, scale=2.0 if ctx.allow_neg_eigval else 1.0)`.
4. The kernel that consumes it is a plain elementwise map — `scale * tl.sigmoid(x)` at
   `fla/ops/common/gate.py:29`, derivative `dy * scale * y * (1-y)` at
   `fla/ops/common/gate.py:48`. Correct for any `scale`; no range assumption.
5. **`allow_neg_eigval` appears NOWHERE else in the KDA op.** Exhaustive grep over
   `/private/tmp/flasrc/c051/fla/` returns hits only in `ops/kda/chunk.py`,
   `ops/kda/fused_recurrent.py`, `ops/gated_delta_rule/chunk.py`,
   `ops/gated_delta_rule/fused_recurrent.py` — i.e. only in the beta-projection wrapper of each
   op. **No Triton chunk kernel, no WY/UT file, no backward file references it.** The chunked
   math is literally unaware of beta's range.
6. **No range assert or clamp on beta exists.** The only assert on beta in `chunk_kda` is a
   *shape* assert — `fla/ops/kda/chunk.py:412`:
   `assert beta.shape == (B, T, HV), ...`. The single guard involving `allow_neg_eigval` is a
   *coupling* check, not a range check — `fla/ops/kda/chunk.py:400-401`:
   `if allow_neg_eigval and not use_beta_sigmoid_in_kernel: raise ValueError(...)`.

### The invariant that a reviewer would expect to break — and why it does not

**CONFIRMED.** The chunked delta-rule family inverts a within-chunk matrix
`(I + tril(diag(beta) K K^T, -1))`. One might expect beta>1 to make it singular. It cannot be:
**the matrix is unit-diagonal and STRICTLY lower triangular, so its determinant is exactly 1
for every beta.**

- The `A` matrix is built with a **strict** lower-triangular mask (`>`, not `>=`), so the
  diagonal is zeroed before any inverse:
  `fla/ops/common/chunk_scaled_dot_kkt.py:76-77` →
  `m_A = (o_t[:, None] > o_t[None, :]) & ...; b_A = tl.where(m_A, b_A, 0)`.
  Note beta is applied at line 74 (`b_A *= b_b[:, None]`) *before* the mask, so beta never
  reaches the diagonal.
- `solve_tril` re-applies the same strict mask and then adds the identity back:
  `fla/ops/utils/solve_tril.py:58` (`m_A = o_i[:, None] > o_i[None, :]`), `:69`, and `:83`
  (`b_A += m_I`). It is a forward substitution on a **unit** lower-triangular matrix.
- KDA's own fused variant does the same: `fla/ops/kda/chunk_intra.py:255-257` masks with `m_A`,
  and `:290-295` adds `m_I` back.
- The reference torch implementation makes it unmissable — `fla/ops/kda/naive.py:123`
  (`mask = torch.triu(..., diagonal=0)`, i.e. diagonal INCLUDED in what gets masked out),
  `:133` (`A = -A.masked_fill(mask, 0)`), `:136` (`A = (A + torch.eye(BT)) * beta[..., None, :]`).

**A second, stronger reason, independently CONFIRMED:** the inversion algorithm contains **no
division at all**. `solve_tril.py:79-83` is pure forward substitution —
`b_a + tl.sum(b_a[:, None] * b_A, 0)`, then `b_A += m_I`. Multiply-add only; no pivot, no
reciprocal. There is nothing that *can* divide by zero regardless of beta. Same structure in the
DPLR twin (`generalized_delta_rule/dplr/wy_fast_fwd.py`) and in the torch reference
(`fla/ops/kda/naive.py:134-136`). Upstream states the contract explicitly in
`fla/ops/utils/solve_tril.py` docstring: *"Compute the inverse of the matrix I + A. A should be
strictly lower triangular, i.e., `A.triu() == 0`."*

So the UT/WY transform is unconditionally invertible in exact arithmetic, independent of beta.
**There is no invariant of the form "nonsingular only for beta ≤ 1."** Unitriangular matrices are
invertible for every real beta, and that is a structural fact, not an empirical one — it is
exactly *why* Grazzi et al. could write "no need to modify the Triton kernel."

### Where the honest residual risk actually is — conditioning, and a real test gap

I was asked to be rigorous in both directions, so: beta ∈ (0,2) doubles the magnitude of the
off-diagonal entries, so the **condition number** of the unitriangular block grows and the
inverse's entries can be larger. Singularity is impossible; precision loss is not. Mitigations
are real but partial, and one is worth naming:

- KDA does the substitution in **fp32** (`fla/ops/kda/chunk_intra.py:252-266`, with the fp32
  diagonal buffer noted at `:790`) **but stores the merged result in `k.dtype`** — bf16 in
  production. That downcast is where a 2x-larger inverse would first show up.
- `FLA_TRIL_PRECISION` defaults to `'ieee'` (`fla/ops/utils/solve_tril.py:19`) — consistent with
  this project's standing note that Triton's fp32 default must be `ieee` for this to be accurate.
- Chunk size bounds the growth: the substitution runs over at most BT=64 rows for KDA, so error
  cannot compound across the sequence.

**CONFIRMED test-coverage gap, and it matters for how much weight to put on "upstream ships it."**
Every upstream KDA/DeltaProduct test builds beta from a plain `.sigmoid()`, i.e. **beta ∈ (0,1)
only** (`tests/ops/test_kda.py:58, 588`; `tests/ops/test_delta_product.py:51, 122`). The two
tests that *are* parameterised on `allow_neg_eigval` (`test_kda.py:176, 743`) are **equivalence
tests, not accuracy tests** — they compare `chunk_kda(beta_raw, allow_neg_eigval=True)` against
`chunk_kda(beta_post*2)`, i.e. **both sides run the same chunked kernel**. They verify the fused
×2 matches the eager ×2 and nothing more. **No upstream test compares a beta>1 chunked result
against `naive_recurrent_kda`**, the fp32 sequential ground truth at `fla/ops/kda/naive.py:59-63`.

By this project's own "empty comparison set reports success" heuristic: upstream green on
`allow_neg_eigval=True` is **not** evidence that the chunked kernel is numerically accurate at
beta ∈ (1,2) — only that two code paths agree. That ground-truth comparison is ours to run, and
it is cheap: one GPU test comparing `chunk_kda` at beta ∈ (1,2) against `naive_recurrent_kda` in
fp32. **I would make that a gate on option 1 below.** Note our tree is well placed to do it —
`src/test/nn/attention/kda_householder_test.py:315-347` already contains the
`chunk_kda_householder` vs `fla.chunk_kda` comparison, but at `beta = rnd(...).sigmoid()`
(`:126`, `:162`) — **beta ≤ 1, so our own equivalence evidence also does not cover the reflection
regime.**

### The literature says this in so many words

**CONFIRMED.** Grazzi et al., *Unlocking State-Tracking in Linear RNNs Through Negative
Eigenvalues*, **arXiv:2411.12537** (v5, ICLR 2025 Oral) — the exact paper our own docstrings
already cite at `recurrent.py:657-658` and `:1454-1455`. Appendix E.4 ("Implementation"),
verbatim:

> "For DeltaNet, implementing the extended eigenvalue range is straightforward, **since there is
> no need to modify the Triton kernel.** However, Mamba requires modifications to the CUDA code
> of the associative scan for both forward and backward passes..."

Figure 13 is the entire diff, captioned "Simple modification to the beta calculation in DeltaNet":
`beta = ...sigmoid()` → `beta = 2 * ...sigmoid()`. §5: the changes "increase the expressivity of
Mamba and DeltaNet while coming at **no additional computational cost**." The Mamba/DeltaNet
asymmetry in that quote is itself the evidence — the authors needed CUDA edits for one and a
two-character edit for the other.

**CONFIRMED.** DeltaProduct (**arXiv:2502.10297**, NeurIPS 2025) agrees — "DeltaNet's eigenvalue
range can be extended from [0,1] to [−1,1], **simply by multiplying β_i by 2**" — and its
Proposition 1 proves that with β ∈ [0,2] and unit-norm keys the Householder product still has
|λ| ≤ 1. So the stability bound survives the widening; this is not a case of trading stability
for expressivity.

**CONFIRMED.** Upstream provenance: fla PR **#919** "[GDN] Support use_beta_sigmoid_in_kernel &
allow_neg_eigval", merged 2026-05-25, added `allow_neg_eigval` to **both KDA and GDN**. The
kernel-side `fused_recurrent` path shows the same one-line treatment —
`fla/ops/kda/fused_recurrent.py:188-191`: `b_beta = tl.sigmoid(b_beta)` then
`if ALLOW_NEG_EIGVAL: b_beta = b_beta * 2`.

**Scope limit worth carrying (CONFIRMED, arXiv:2411.12537 §E.4):** the trick is *not* universal.
Models that accumulate gates in **log space** (Mamba2, GLA, mLSTM) cannot do this directly, and
"early tests on the chunkwise parallel form of GLA showed degraded performance." It is safe for
DeltaNet/KDA specifically because **beta is not accumulated in log space** — only the decay `g`
is. That is a real invariant, and it is satisfied here.

### Therefore

**CONFIRMED:** the mechanism `KDA_R1` was built to isolate — "beta-in-(0,2) reflection regime
ALONE, at KDA's throughput" (`core6_arms.py:442-447`) — was obtainable by setting
`allow_neg_eigval=True` on `KimiDeltaAttentionConfig`, which the class already supports at
`recurrent.py:1088`. The arm instead routed through `KimiDeltaHouseholder(num_householder=1)`,
whose kernel is **by its own module docstring** *"a simple fused-recurrent
(sequential-over-time) Triton kernel, not a chunked WY-representation kernel"* and *"expected to
be materially slower than fla's chunked kernels; the goal of this milestone is mechanism
validation, not throughput"* — `src/olmo_core/nn/attention/kda_householder.py:64-70`.

**The 22% (0.779x) penalty at R=1 is an avoidable routing artifact, not a price of negative
eigenvalues.** So is the +23.7% reserved memory, and so — SUSPECTED but well-motivated — is the
17x sd blow-up (sd 0.04516), since the two paths compute the same function and differ only in
accumulation order and chunking.

**Cost of the fix: hours, not days.** Category **(i)** — shipped code we already call.

### One caveat, stated plainly so it is not oversold

`KDA_R1` and `allow_neg_eigval=True` on `KimiDeltaAttention` are the same *function* but will
not be *bit-identical*: the Householder path L2-normalises q/k in the layer
(`recurrent.py:1669-1670`) and computes the gate in the layer (`:1635-1638`), whereas
KimiDeltaAttention lets the fused kernel do both (`:921-922`). Also
`allow_neg_eigval=True` on `chunk_kda` requires `use_beta_sigmoid_in_kernel=True`
(`fla/ops/kda/chunk.py:400-401`), i.e. the layer must pass **raw beta logits** and let the
kernel apply `2*sigmoid`, instead of pre-applying `.sigmoid()*2` as `recurrent.py:874-876`
does. Two equally valid routes:
- **(a) Zero-kernel-change route:** keep `recurrent.py:874-876` as-is (post-sigmoid beta in
  (0,2)) and do **not** set the fla flag. Nothing in the chunked op constrains beta's range —
  see the invariant analysis above — so passing beta in (0,2) as a plain post-sigmoid tensor
  works today with **no code change at all** beyond `allow_neg_eigval=True` on the config. This
  is the minimal-diff option.
- **(b) Fused route:** thread `use_beta_sigmoid_in_kernel=True, allow_neg_eigval=True` through
  `dispatch_chunk_kda` (which currently exposes **neither** — see
  `src/olmo_core/nn/attention/flash_linear_attn_api.py:45-59`, no such parameters) and pass raw
  logits. Saves one elementwise pass. ~1 engineer-day including the dispatch plumbing.

Route (a) costs essentially nothing and is what I recommend for the production decision.

## Item 3 — the R>1 plan on record

The HANDOFF next-step ⓶ (`docs/mixer-bakeoff/HANDOFF.md:226-240`) proposes packing Householder
factors onto `chunk_dplr_delta_rule` and says *"Do not patch `chunk_gated_delta_product`: the
per-head scalar gate is baked into six sites across four files plus the whole backward."*

### Finding 3a — a cheaper option than DPLR exists and the HANDOFF's stated risk is already retired upstream

**CONFIRMED:** `fla.ops.gated_delta_product.chunk_gated_delta_product` **is already a chunked
WY-representation kernel** in 0.5.1, not a sequential scan:
`fla/ops/gated_delta_product/chunk.py:64-77` calls `chunk_scaled_dot_kkt_fwd` then `solve_tril`
(the same UT transform KDA uses), `:79-96` `recompute_w_u_fwd`, `:97-107`
`chunk_gated_delta_product_fwd_h`, `:108-118` `chunk_gated_delta_product_fwd_o`. It has a full
autograd Function (`:122-255`).

**CONFIRMED — the HANDOFF's "riskiest unknown" is empirically retired.** The HANDOFF names as
its top risk *"whether DPLR's chunked backward is well-conditioned with `gk=0` and `q=0` on R−1
of every R positions."* fla's own production DeltaProduct backward **does exactly that
zero-padding trick and ships it**:
- `fla/ops/gated_delta_product/chunk.py:212-217`:
  ```
  q_new = q.new_zeros(q.shape[0], q.shape[1], ctx.num_householder, q.shape[2], q.shape[3])
  q_new[:, :, -1] = q
  do_new = do.new_zeros(...); do_new[:, :, -1] = do
  ```
  i.e. **q and do are zero on R−1 of every R positions, with the real value on the LAST factor**
  — precisely the mapping the HANDOFF proposes.
- The gate is zero-padded the same way in the forward,
  `fla/ops/gated_delta_product/chunk.py:41-43`: `g_interleaved` is `new_zeros`, then
  `g_interleaved[:, :, 0] = g` — **decay on factor 0, zero on 1..R−1**, exactly the HANDOFF's
  mapping. This also CONFIRMS the docstring claim at
  `src/olmo_core/nn/attention/kda_householder.py:26-30`.
- It then reuses the ordinary `chunk_gated_delta_rule_bwd` on the interleaved axis
  (`:221-234`), with a candid `# TODO: optimize the backward pass like the forward pass` at
  `:218-219`.

So "q=0 and gate=0 on R−1 of every R positions, through a chunked backward" is **not an
unknown** — it is upstream's shipped, tested configuration. That materially lowers the risk the
HANDOFF assigns to next-step ⓶. (It does not prove the *DPLR* backward specifically is fine —
that is a different kernel — but it removes the structural objection to the padding pattern.)

### Finding 3b — the actual blocker for R>1 is one shape assert, and the helper it needs already supports 4-D

**CONFIRMED:** the only thing stopping `chunk_gated_delta_product` from taking KDA's
per-channel gate is a single assert:
`fla/ops/gated_delta_product/chunk.py:344` → `assert g.shape == (B, T, H)`.
(Identical in 0.4.1 at `fla/ops/gated_delta_product/chunk.py:275`, so this did not change
across the pin.)

**CONFIRMED:** the cumsum helper it calls is already rank-polymorphic —
`fla/ops/utils/cumsum.py:446-467`: `chunk_local_cumsum` dispatches to
`chunk_local_cumsum_scalar` for `ndim==3` and **`chunk_local_cumsum_vector` for `ndim==4`**. So
the gate-cumsum step needs no work.

**CONFIRMED — but the downstream kernels genuinely are per-head scalar**, which is where the
HANDOFF's "six sites" estimate comes from and it is basically right:
- `fla/ops/common/chunk_scaled_dot_kkt.py:96-97` documents `g` as `[B, T, HV]` and loads it as a
  1-D block at `:69-71` (`p_g = tl.make_block_ptr(g + bos*HV + i_h, (T,), (HV,), ...)`,
  `b_g_diff = b_g[:, None] - b_g[None, :]`) — scalar per (t, head).
- `fla/ops/gated_delta_product/chunk_deltaproduct_h.py:156-160` and `:307-311` likewise index
  `g + bos*H + i_h` with a scalar stride.
- Contrast KDA's own per-channel versions, which already exist and are the code to copy from:
  `fla/ops/kda/wy_fast.py:101-103` (`p_gk = tl.make_block_ptr(gk, (T, K), (HV*K, 1), ...)`,
  `b_kb *= exp2(b_gk)`) and `fla/ops/kda/chunk_intra.py` generally.

### Finding 3c — the DPLR mapping in the HANDOFF is correct

**CONFIRMED** against the DPLR reference recurrence, `fla/ops/generalized_delta_rule/dplr/naive.py:11`:
`S_t = S_t @ (I + alpha_t beta_t^T) + v_t k_t^T`, implemented at `:34-35`:
```
_kv = _k[..., None]*_v[..., None,:] + (S*_alpha[..., None]).sum(-2, keepdim=True)*_beta[..., None]
S = S*gk[:,:,i].exp()[..., None] + _kv
```
Setting `a = k` and `b = -beta*k` gives the transition `(I - beta k k^T)` and the drive
`beta*k v^T` requires `k` scaled by beta on the additive term. The HANDOFF's stated mapping
(`a_r = k_r`, `b_r = -beta_r k_r`, decay on factor 0, `q` on last factor) reproduces the
Householder product correctly **up to that beta scaling on the `k v^T` term**, which the wrapper
must handle (pass `k_r * beta_r` as the `k` argument, or fold beta into `v`). Signature
confirmed: `chunk_dplr_delta_rule(q, k, v, a, b, gk, ...)` with
`gk` documented as `[B, T, H, K]` log-space decay —
`fla/ops/generalized_delta_rule/dplr/chunk.py:442-473`. **CONFIRMED no assert on `gk` content or
on `q`** — the only asserts in that function are CP-related and batch-size-related
(`:518-535`). It has a real chunked backward (`ChunkDPLRDeltaRuleFunction.backward` at
`:235-436`).

**Caveat — and this one is CONFIRMED, not suspected, and it downgrades option 5.** DPLR is not
merely "the more general formulation"; its chunked kernel **runs at chunk_size=16 instead of 64**,
a 4x smaller chunk, for documented numerical reasons.
`fla/ops/generalized_delta_rule/dplr/chunk.py:156-158`, verbatim:

> `# Due to gate numerical stability consideration, we only support chunk_size=16 when safe_gate=True`
> `# And in practice, chunk_size=16 is sufficient for no safe gate situations.`
> `# It's different from the other chunk implementations.`

Compare `chunk_kda`, which requires 32 or 64 (`fla/ops/kda/chunk.py:390-392`). A 4x smaller chunk
is a direct throughput cost — the whole point of chunking is to convert the sequential recurrence
into tensor-core matmuls, and BT=16 gives up most of that. Additional confirmed DPLR warts:
- `dplr/chunk.py:507-513` warns fp32 is unsupported "on some platforms ... If you want to use
  float32, please solve the issue by yourself" (and mis-names the function in its own message).
- `dplr/chunk_A_fwd.py` allocates `Aab`/`Aak` in fp32 with the comment "involving matrix inverse
  and it'd be better to use float here" — a conditioning concession.
- Its gate path takes a **reciprocal** of the decay (`exp2(-b_gi + b_g_last)` in
  `dplr/chunk_A_fwd.py:101-106`), which overflows for very negative `gk`. This is the real reason
  `safe_gate` exists there, and it is a hazard our KDA gate (which can go quite negative) would
  walk straight into.
- Open upstream bugs in this exact kernel: #1084/#1085, "Safe-gate DPLR kernels use the wrong
  midpoint offset for multi-head inputs" (2026-07-31) — i.e. the safe-gate DPLR path was
  **broken for multi-head inputs as of five weeks ago**.

**Revised judgement on HANDOFF next-step ⓶:** the mapping is correct and the named risk is
retired, but DPLR is a worse target than the HANDOFF assumes. It would fix the **memory** cliff
(1.00 GiB → 32 MiB) credibly; I would **not** expect it to recover the throughput, and it carries
live upstream bugs. If R>1 is pursued, **option 4 (widen `chunk_gated_delta_product`'s gate to
4-D) is the better target** — it keeps BT=64, keeps the KDA-family numerics, and its backward
already ships the zero-padding pattern.

### Finding 3d — "R reflections as a single rank-R update via WY" is (iii), and there is a reason
**SUSPECTED.** A product of R Householder reflections *is* exactly a rank-R update
(`I + U W U^T` form; that is what a WY representation is), so this is mathematically available.
But no fla kernel takes a rank-R-per-token update with a per-channel gate, and writing one is
new-kernel work with a hand-derived backward. Category (iii), weeks. Not recommended.

### The answer: what made it fast, and does it port to R>1

**CONFIRMED, ranked by size of effect.**

**① The lower-bounded forget gate — the biggest change, and it is an algorithm change made *for*
the kernel.** K3 §2.1.1 replaces `g = -exp(A)·softplus(z) ∈ (-∞,0)` with
`g = g_min·sigmoid(exp(A)·z) ∈ (g_min, 0)`, `g_min = -5`. The paper's own reasoning: Eq. 4
rescales keys by `1/Γ`, which "can grow without bound and overflow in finite precision." Kimi
Linear worked around it by splitting each chunk into secondary 16-token tiles where "the diagonal
tiles ... still require explicit position-pair computations, which remain **the main intra-chunk
bottleneck**." With `g_min=-5`, cumulative log-decay over a 16-token tile lies in (-80,0), the
reciprocal stays inside bf16 range, and "this finite range allows **both diagonal and
off-diagonal tiles to use dense Tensor Core matrix multiplications, eliminating the position-pair
diagonal path**." Figure 3b captions it "Position-pair Diagonal → Tensor Core."
Visible in code as **two different diagonal-tile algorithms selected by the flag** —
`fla/ops/kda/chunk_intra.py:825-859` dispatches the dense-`tl.dot` sub-chunk kernel when
`safe_gate` else the per-position `tl.sum` loop in `chunk_intra_token_parallel.py`. fla commit
`d1097c60` is literally **"[KDA] Speed up chunk_kda by introducing lowerbound gate"** (2025-12-30).
**→ Applies at R>1 (b).** The overflow being fixed is in the *decay* envelope `1/Γ`, a property of
`Diag(α_t)`, independent of how many reflections multiply it. **This is the single most portable
finding in the audit, and it is the same knob as HANDOFF ⓹ change 1 — which our dispatch does not
expose.**

**② `a = b = k` binding — this is the "~2x vs DPLR" claim, and it does NOT port.** §3.2: "By
binding both variables a and b to k, KDA effectively alleviates this bottleneck—reducing the
number of second-level chunk matrix computations **from four to two**, and further eliminating
three additional matrix multiplications. As a result, the operator efficiency of KDA improves by
roughly **100%** compared to the DPLR formulation," with "nearly 2x the speed of DPLR for sequence
lengths up to 64k" (Fig. 2 — **batch 1, 16 heads, a single config, not a sweep**). Confirmed
bespoke: `grep -rn "dplr" fla/ops/kda/` returns nothing.
**→ R=1 ONLY (a).** At R>1 each timestep has R distinct `k_r`, so there is no single `k` for `a`
and `b` to bind to and the 4→2 collapse dissolves. **This is the deep reason a DeltaProduct R>1
operator cannot simply inherit KDA's speed — and, note, the reason HANDOFF ⓶'s DPLR plan is
targeting the formulation KDA was built to beat by 2x.**

**③ Gate + L2norm + beta-sigmoid fused into the kernel; gate activation fused with the chunk
cumsum.** Nov 2025 had a standalone `fused_kda_gate` called from Python; by K3 it is inside
`chunk_kda`. K3's module carries the tombstone at line 49:
`# from fla.ops.kda.gate import fused_kda_gate  # deprecated, gate is now computed inside chunk_kda`.
The fused kernel is `kda_gate_chunk_cumsum_vector_kernel` (`fla/ops/kda/gate.py:362-432`), which
computes the activation and immediately `tl.cumsum`es it. **→ (b), R-agnostic.**

**④ `exp` → `exp2` throughout**, by folding `log2(e)` into the cumsum scale (`RCP_LN2` at
`chunk_fwd.py:51,60`) so every kernel-side exponential is a hardware `exp2`. fla commit `ea58f333`.
**→ (b).**

**⑤ Fusing the inter-chunk computation with the triangular solve** — fla commit `8d8bfcd4`
(2025-11-27), whose message ships its own benchmark: *"reducing kernel launches from 3 to 2 and
eliminating intermediate memory I/O"*, **~1.5x average, up to 1.59x**. **→ (b).**

**⑥ Token-parallel intra-chunk attention** (`chunk_intra_token_parallel.py`, one block per token,
varlen padding waste removed). **→ (b)** — but note this is the path `safe_gate=True` *replaces*,
so in K3's production config it is the fallback, not the hot path.

**⑦ FlashKDA — a CUTLASS rewrite, and it is NOT available to us.** K3 §5.1.1 describes it;
`MoonshotAI/FlashKDA`, 1187 stars. Measured **1.85x** over Triton `fla_chunk_kda` on H20 fixed-length
(up to 2.29x varlen), **2.31x** on GB200 (up to 3.27x). Two structural lessons: it uses
**CHUNK=16, not 64** (a *consequence* of ① — bounding the gate let them shrink the chunk and delete
the rescaling machinery, and a 16x16 inverse comes straight from a Neumann series), and it
**de-fused** K1/K2 into two kernels because "early prototypes ... used a single fused kernel
[where] token-parallel work ... was bottlenecked by the much lower parallelism of the recurrence,
leaving a large fraction of the SMs idle. Splitting the pipeline into two kernels yielded **at
least a 15% end-to-end speedup**" — the counter-lesson to ⑤.
**→ Irrelevant to this decision, three ways: it is inference-only** (`flash_kda.py:63-88` rejects
when `torch.is_grad_enabled()`), **it requires K=V=128 exactly**, and **our bake-off geometry is
`HEAD_DIM = 64`** (`core6_arms.py:99`). Do not put it in a training-throughput plan.

**⑧ KDA Context Parallelism (KCP)** — K3 §5.1.2. Vanilla linear-attention CP fails for KDA
because "KDA's delta rule applies the token-dependent matrix M_t to the incoming state before
adding the current write," so a from-zero local state is insufficient. KCP decomposes each segment
into a cumulative transition and a from-zero state that "compose associatively," recovered by a
prefix scan with a fixed-size all-gather. **→ (b), and this is good news for R>1**: associativity
is a property of `M_t` being *any* matrix, and a product of R reflections is still a matrix.

**⑨ Mixed precision — no single answer, so do not "port bf16 state" as a slogan.** The Triton path
keeps **fp32** recurrent state (`chunk.py:383` asserts it), a **separate fp32 buffer for the
diagonal 16x16 blocks** (`chunk_intra.py:790`), and **tf32-or-ieee** for the solve
(`chunk_intra.py:20-23,300`). FlashKDA does the opposite — **bf16** on-chip state ("as long as the
state update itself is performed with fp32 FMA") and **fp16** for the 16x16 inverse, justified by
the inverse's elements being bounded in [-1,1]. **That last argument is (a)** — the bound is a
property of the single-reflection series and was not verified for an R>1 product. Do not port it
on faith.

**⑩ Determinism/reproducibility: UNSUPPORTED — nothing found, and I looked hard.** Zero relevant
hits across the Kimi Linear full text, the K3 full text, the FlashKDA repo, and all 72 commits to
`fla/ops/kda/`. No `atomic_add` anywhere in the KDA op (checked — atomics are the usual split-k
nondeterminism source), and `tests/ops/test_kda.py` is reference-agreement at rtol=1e-4, not a
batch-invariance test. **So the lead's premise that "Kimi made it reproducible" is not something I
can confirm; the public evidence is that they made it *fast*.** SUSPECTED and worth flagging as
open risk: KDA is structurally batch-variance-prone — `mode` switches chunk↔fused_recurrent on
sequence length, `safe_gate` switches the diagonal algorithm, FlashKDA auto-dispatches under
`inference_mode` with `default_enable=True` (so the same call is numerically different depending on
whether grad is on and whether a package is installed), autotune picks tiles by measured timing,
and the solve precision is tf32-or-ieee *by hardware capability*.

**Two paper-level gaps worth recording because this project has cited numbers:**
- **No MFU figure exists in arXiv:2510.26692** (`grep -c MFU` over the full 28 pages = 0). It
  reports latency, TPOT (6.3x at 1M), prefill (2.3x@512K, 2.9x@1M) and a 1.16x compute-efficiency
  scaling-law fit. Any "KDA MFU" number in our notes did not come from that paper.

## Direct answer to the lead

**Yes — and for the case you actually care about it is already free, which is a stronger result
than "it can be optimised."** Negative eigenvalues are not a kernel feature; they are a
one-line change to how beta is projected — `2*sigmoid(x)` instead of `sigmoid(x)` — and fla's
fast chunked `chunk_kda` has shipped that as a named argument all along
(`fla/ops/kda/chunk.py:190, 241-245`), implemented as literally one scale factor on a fused
sigmoid (`:62`, `:170`) and referenced by **no** Triton kernel anywhere in the op. The paper we
already cite in our own docstrings says so outright — arXiv:2411.12537 §E.4: "For DeltaNet,
implementing the extended eigenvalue range is straightforward, **since there is no need to modify
the Triton kernel**," at "no additional computational cost," with a two-line diff as its Figure 13.
There is no range assert, no clamp, and no invariant that beta≤1 protects: the matrix the chunked
WY/UT transform inverts is masked strictly below the diagonal and has the identity added back
(`solve_tril.py:58,69,83`), so it is unit-triangular with determinant exactly 1 for any beta, and
the substitution that inverts it contains no division at all. Our own `KimiDeltaAttention` already
contains the two lines
(`recurrent.py:874-876`) behind an `allow_neg_eigval` flag it exposes at `:1088`, and our
`GatedDeltaNet` has been training with beta in (0,2) on a chunked kernel by **default**
(`:147`, `:513`) for the whole project. So the honest reading of the bake-off is that the 22% at
R=1 measured our *stand-in* kernel — whose own docstring says it is a sequential fused-recurrent
scan, "expected to be materially slower," built for "mechanism validation, not throughput"
(`kda_householder.py:64-70`) — and not the cost of negative eigenvalues. Flip the flag on
`KimiDeltaAttentionConfig` and you get the R=1 mechanism at 1.000x throughput, at KDA's memory,
in under a day — with one caveat I would enforce rather than hand-wave: nobody, upstream or here,
has ever compared a beta>1 **chunked** result against the fp32 sequential reference (upstream's
`allow_neg_eigval` tests compare the chunked kernel to itself, and our R=1 test uses beta ≤ 1), so
spend half a day on that one accuracy test first. On the Kimi analogy: it is real, I can name each
piece, and it is worth being precise about what it does and does not buy. K3 did speed KDA up a lot
since the November paper — a lower-bounded forget gate that keeps the reciprocal decay inside bf16
range and thereby converts the diagonal tiles from per-position arithmetic to dense Tensor Cores
(K3 §2.1.1; the fla commit is titled "Speed up chunk_kda by introducing lowerbound gate"), gate and
L2norm and beta-sigmoid fused into the kernel, `exp`→`exp2`, inter-chunk fused with the triangular
solve for a measured ~1.5x, and a CUTLASS rewrite (FlashKDA) at 1.85–2.31x over Triton. **Three
corrections to the framing, though.** First, there is no K2 waypoint — K2 is pure MLA and mentions
KDA zero times; the lineage is Kimi Linear → K3. Second, and this is the load-bearing one: **Kimi's
headline ~2x is specifically "KDA vs DPLR," and it is bought by binding `a = b = k`, which is
exactly what an R>1 Householder product destroys** — at R>1 every timestep has R distinct `k_r`, so
the four-to-two collapse of second-level chunk matrices dissolves. "Make R>1 as fast as KDA by
copying Kimi" is therefore not on the table; the portable parts are the gate bound, the fusions,
`exp2` and the context-parallel decomposition, while the biggest single win is structurally
R=1-only. Third, FlashKDA is **inference-only and needs head_dim 128** — we run 64 — so it is not in
play for training throughput at all. I also could not confirm the reproducibility half of the
analogy: zero relevant hits across both papers, the FlashKDA repo, and all 72 commits to
`fla/ops/kda/`; the public evidence is that they made it fast, not that they made it deterministic.
Net: you need none of this for R=1, and for **R>1** — where the remaining 10.9% arity cost and the
fp32 state-history memory cliff live — the news is still better than the handoff assumed, because
its "riskiest unknown" (whether a chunked backward tolerates `q=0` and `gate=0` on R−1 of every R
positions) is upstream's own shipped configuration (`gated_delta_product/chunk.py:41-43, 212-217`).
The real remaining work is widening two scalar-gate Triton kernels to a per-channel gate, ~8–15
days — and I would retarget it away from the handoff's DPLR plan, since DPLR runs at chunk_size 16
versus KDA's 64 and is the very formulation KDA was designed to beat. Given this run found **no CE
gain** behind R>1, I would not spend those days yet. **The one thing I would do this week is
options 1 and 2, which are both config-and-dispatch work on the fast kernel we already call.**
