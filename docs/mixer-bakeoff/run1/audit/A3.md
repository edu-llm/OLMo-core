## 3. "Peak-memory sd is exactly 0.000 within every arm, so those ratios are mechanism rather than variance"

**Location:** `HANDOFF.md:169-170` (Key decisions ①), `RESULTS-TABLE.html:226-227`.

Recomputed: sd of `peak_memory_gib` within every one of the 6 arms is **0.0 to 15 decimal places**
(e.g. all three KDA_BASE cells report `9.153131484985352` verbatim). The number is **CONFIRMED exactly**.

| Claim | Verdict | Notes |
|---|---|---|
| "so those ratios are **mechanism** rather than variance" | **SUSPECTED logic overreach.** Zero seed-to-seed variance in peak memory is expected and close to tautological — GPU peak allocation for a fixed static graph (shapes/dtypes/batch/seqlen) does not depend on the random seed at all, so "ruling out seed noise" rules out a threat that was never live. The real threat the run itself documents is a **third explanation neither "mechanism" nor "variance"**: per `HANDOFF.md`'s own Next steps ⑥, `solve_widths` had a bug that mis-sized each arm's FFN-width correction (up to 21× out of the 0.05% param-matching tolerance before the fix) — meaning part of every arm's memory footprint reflects its own **arm-specific width respend**, not purely the mixer operator's native cost. "Mechanism" implies the delta is attributable to the *mixer*; it could equally be (partly) attributable to the *width correction each arm needed to hit the param target*. | "Peak-memory sd is exactly 0.000 within every arm — expected, since allocation for a fixed compute graph is seed-independent. The cross-arm deltas are reproducible and not seed noise, but they also include each arm's own FFN-width correction from parameter-matching, not solely the mixer's native memory cost." |
