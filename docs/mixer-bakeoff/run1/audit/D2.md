# D2 — Devil's Advocate: Mixer Bake-off Run 1

**Target:** "Use `KDA_BASE` or `KDA_NOACT`, decided on throughput/memory because CE is
unresolved. Do not ship `KimiDeltaHouseholder`. Gated conv is a bound, not a benefit. GDN2 is
worse." (`docs/mixer-bakeoff/HANDOFF.md`, `docs/mixer-bakeoff/run1/REPORT.md`, branch
`edullm/mixer-bakeoff`, worktree `claude-bakeoff--mixer-bakeoff`.)

All numbers below verified against `docs/mixer-bakeoff/run1/cell-*.json`, `results.json`,
`REPORT.md`, `PREREGISTRATION.md`, `HANDOFF.md`, and `src/olmo_core/nn/attention/recurrent.py` /
`src/olmo_core/nn/transformer/core6_arms.py` on that branch. Git log for
`docs/mixer-bakeoff/` confirms the commit timeline cited below.

## Ranked objections

### 1. "GDN2 is worse" is built on the statistical pathway the pre-registration subordinated — GROUNDED, DECISION-CHANGING

The pre-registration (`PREREGISTRATION.md` §4.5) commits to **Levene as THE decision test**: if
it rejects, fall back to Welch/Games-Howell (T3 for a one-control design); if it does not reject,
"the pooled analysis stands." Levene: **p = 0.484 — does not reject.** `REPORT.md` §2.2 says so
explicitly: *"Levene does not reject; the pooled analysis stands."*

Under that pooled analysis (`REPORT.md` §2.4, the pre-registered primary path), GDN2's Dunnett
contrast is **+0.03705 nats, CI [−0.01131, +0.08542], adj. p = 0.1585 — does not exclude zero,
does not clear the MDE.** By the study's own committed rule, GDN2 is in exactly the same "not
resolved" bucket as every other arm.

"GDN2 is worse" only survives by reaching for the **non-primary** Welch/Dunnett-T3 fallback
(triggered by Bartlett, p = 0.0059, which the pre-registration did **not** designate as the
decision test), which gives CI [+0.0262, +0.0479]. HANDOFF itself hedges this correctly in one
place ("Both readings are in the report; neither is presented as settled") — but the four-line
recommendation under attack drops the hedge and states "GDN2 is worse" as a flat conclusion, and
Next Steps ⓸ calls it "the only contrast significant under any test," which is true only by
switching to the test the pre-registered rule didn't select. A reader who takes the
recommendation's summary line at face value gets a stronger claim than the pre-registered
statistics support.

**Why this changes the decision:** if GDN2 is put back in the "not resolved" bucket with
everything else — which is what the primary, pre-committed test says — then the case against it
is *identical* to the case against gated-conv or Householder: a null. GDN2 also has the
**highest measured MFU in the entire run (42.0%)** and near-tied throughput (0.994×) and memory
(1.020×) with the recommended arms. Nothing about the co-primary, budget-independent endpoints
argues against it. The only thing carrying "don't ship GDN2" is a contested secondary test.

### 2. The "kernel, not mechanism" argument against Householder rests on a control that isn't clean — GROUNDED, DECISION-CHANGING

HANDOFF's celebrated finding (§ "What worked ⑤") is: `KDA_R1` is "parameter- and FLOP-identical
to `KimiDeltaAttention` … **and the same function**," so its 0.779× throughput proves "kernel
overhead alone = 28.6%; the arity step R=1→R=2 costs a further 10.9%." Next Steps ⓷ repeats this
to justify "Never ship `KimiDeltaHouseholder` at R=1," attributing its 17×-outlier variance
(sd 0.04516) to "suspected kernel-induced instability."

But `core6_arms.py` itself contradicts the "same function" framing. `KDA_R1`'s registry note
(lines 442–448) says: *"the Householder operator at R=1, with `allow_neg_eigval=True`. Isolates
ARITY from the reflection regime: … `KDA_R1 − KDA_BASE` is the **beta-in-(0,2) reflection regime
ALONE**."* `KDA_BASE` (`kda-paper`) has `allow_neg_eigval=False` (`PREREGISTRATION.md` row 1;
`recurrent.py:1088` default). `recurrent.py:258-260` shows what this flag does: `beta =
beta*2.0`, widening the erase-gate range from a **contraction** `[0,1]` to a true **reflection**
`[0,2]` — the exact mechanism `arXiv:2411.12537` (negative eigenvalues, state-tracking) is about,
and the same mechanism `KDA_R2`'s own note calls "LOAD-BEARING" (line 458: *"at the class default
of False beta stays in (0,1) … and the mechanism the arm is named for is absent while everything
still trains"*).

So `KDA_R1` vs `KDA_BASE` is **not** isolating kernel cost from mechanism cost on the CE axis —
by the registry's own words, it isolates a *different* mechanism (the reflection regime) layered
on top of a different kernel. The throughput argument is probably fine (`beta*2.0` is a scalar
multiply, unlikely to explain 21% slower steps); the CE/variance argument is not. R1's outlier
variance (17× the best arm, and the CE mean itself is the 3rd-worst in the table) has an
un-examined alternative explanation sitting in the same file that names the mechanism as
load-bearing. The proposed "cheap check" (rerun R1 on `backend="torch"`) **cannot distinguish
the two candidate causes**, because both backends would still run with `allow_neg_eigval=True`.

**Why this changes the decision:** "do not ship `KimiDeltaHouseholder`" is currently supported by
attributing 100% of its bad behavior to a kernel that's already scoped and fixable (see #6). If
some of that bad behavior is actually the reflection-regime dynamics interacting badly with a
0.6B-token budget (a training-stability question, not an implementation question), then fixing
the kernel would not fix the arm, and the correct read of this run is "we don't yet know," not
"never ship."

### 3. GDN2's headline number is exactly the shape of effect the project's own data says shrinks fastest with budget, measured at half the calibration point — GROUNDED, DECISION-CHANGING

This run's TPP is **1.5** (599.8M tokens/cell). A sibling in-tree audit
(`KDA-LIV/docs/claude-audit/07-token-budget.md`, lines 196–214, citing `arXiv:2607.07953` Table 7
at 350M params) already measured, in-domain: **Gated DeltaNet's edge over baseline shrinks
0.0103 nats @1B tokens → 0.0059 nats @15B (×0.57), and a further ×0.32 by 40B.** That is the
*same family* of effect (a gated-delta-rule variant vs. a baseline) as GDN2's measured
**+0.0371-nat deficit** here — and this run's 0.6B-token cells sit at **half** the token count of
even the "1B" calibration point where the un-shrunk 0.0103 was measured. If GDN2's deficit
follows anything like that decay curve, the number that currently reads as "the largest, most
significant effect in the run" is also the one the project's own precedent predicts to shrink the
most going into a production-scale run (this project's flagship already trains at TPP 27–44 —
well past the 15× and 40× budget points where the precedent shows most of the effect evaporating).

Compounding this: GDN2 was run at `expand_v=1.0` and `allow_neg_eigval=False`
(`recurrent.py:2352-2369`), which the config's own docstring flags as **not** parameter-matched
to `GatedDeltaNetConfig`'s defaults (`expand_v=2.0`) and **not** using the extended dynamics that
`KDA_R1`/`KDA_R2` get. "GDN2 is worse" is a verdict on one specific, minimal-state,
paper-headline configuration of the family — not on the mechanism.

### 4. Nothing about decode/inference was measured, and the codebase itself carries per-arm state-size differences that predict decode-cost differences invisible in this design — GROUNDED, DECISION-CHANGING

The endpoint is aggregate `val_ce` at seq-len 4096 and **prefill-style steady-state training
throughput**. Every arm here is a linear-attention/recurrent mixer whose entire practical
argument over softmax attention is an O(1)-in-context **decode** path with a fixed-size
recurrent state — and that path was never run, never timed, never measured for memory. The run
compares six operators on the one workload (long-batch training) where they're closest to each
other, and is silent on the one workload (single-token autoregressive decode with KV/state reuse)
where they're most likely to differ and where production inference cost actually lives.

This is not a hypothetical gap. The codebase's own state-size knobs differ by arm in ways that
should show up in decode:
- `GatedDeltaNet2Config.n_v_heads` docstring (`recurrent.py:2344-2346`): *"the recurrent state
  has shape `(n_v_heads, head_k_dim, head_v_dim)` and does not grow with sequence length, so
  raising `n_v_heads` buys long-range capacity rather than costing memory"* — i.e., state size
  and recall capacity are explicitly linked in-tree, and GDN2 here runs at the *minimal*
  `expand_v=1.0` state.
- `KimiDeltaHouseholderConfig`'s docstring warns its **backward** allocates an
  `O(B·T·H·K·V)` fp32 workspace "proportional to sequence length" that "can OOM at production
  shapes even when the forward fits comfortably" — a decode/long-context risk that this run's
  4096-token, forward-dominated training profile would not surface, and that HANDOFF's own Next
  Step ⓶ says chunking would shrink 1.00 GiB → 32 MiB (i.e., the current run's memory numbers for
  R1/R2, 13.26/13.39 GiB reserved, are an artifact of the unchunked backward, not the operator).
- The in-tree literature review (`KDA-LIV/docs/claude-audit/07-token-budget.md` line 320, citing
  Zoology arXiv:2312.04927) states aggregate perplexity gaps between recurrent and
  attention-family models **shrink** with scale (2.14 → 0.59 → 0.35 nats at 70M → 160M → 360M)
  **while the recall-attributable share of that gap rises toward ~100%** — i.e., exactly the
  regime this bake-off is in (small model, aggregate CE) is the regime where CE is *least*
  informative about the mechanism differences that matter, and decode/recall is where they'd show
  up.

**What this could cost:** shipping on throughput/memory-at-training with zero decode
measurement risks picking the arm that is fastest to *train* and worst to *serve* — precisely
inverted from what "choose the production mixer" should optimize, given the team's own framing
(§ Goal) is explicitly a production choice, not a paper result.

### 5. The pre-registered escape hatch for an unresolved CE — the sliced/recall endpoint — was never wired, and it's the cheapest fix available - GROUNDED, DECISION-CHANGING

`PREREGISTRATION.md` §3 pre-registers a **secondary endpoint**, `sliced_eval`, precisely for the
scenario that happened: "the thing that distinguishes these mixers may live in recall, not
aggregate CE" (HANDOFF Next Steps ⓵, option 2), described there as "the highest
value-per-GPU-hour change available" and "a re-weighted pass over held-out text at **zero extra
training cost**." `REPORT.md` §5 confirms: *"`sliced_eval` is null unless `--slice-mask-uri` was
set… Secondary means secondary; it moves no gate."* Every one of the 18 cell JSONs has
`"sliced_eval":null`.

So the one measurement this design pre-committed to as the fallback when CE didn't resolve — and
CE did not resolve — was not taken, on a run that already had checkpoints in S3
(`teams/scratch/runs/run_019fe0f9-…/cell-*/checkpoints/`, per HANDOFF ⓺) that could in principle
be re-scored against a slice mask without retraining anything. The recommendation proceeds
straight to "fall back to throughput and memory" without paying for the cheap option that was
designed in for exactly this outcome.

### 6. Rejecting Householder "on the mechanism" is rejecting a known, scoped, already-costed implementation gap — GROUNDED, mostly CAVEAT-ONLY but sharpens #2

HANDOFF's own Next Step ⓶ says the Householder kernel's memory/throughput penalty is fixable:
pack onto `fla.ops.generalized_delta_rule.dplr.chunk_dplr_delta_rule` (already chunked, already
takes a per-channel gate), estimated **4–7 engineer-days**, "the math survives R>1 *exactly*."
It explicitly separates the two questions: *"chunk it to make R>1 shippable, not because R>1 is
currently winning."* `KDA_R2` has the **2nd-lowest sd in the entire run** (0.00642, beaten only
by `KDA_NOACT`'s 0.00258) and a CE mean better than both `KDA_R1` and `GDN2`. If the ~28.6%
kernel tax (and the R2-specific further ~10.9%, itself confounded per #2) is fixed, the
throughput/memory case against Householder mostly disappears, leaving only the still-unresolved
CE contrast — the same "not resolved" status every other arm gets. "Do not ship
`KimiDeltaHouseholder`" as an unqualified, standing conclusion forecloses re-examining the
mechanism once the (already-scoped) kernel work lands; "do not ship **until chunked**" is the
claim the evidence actually supports.

### 7. Throughput/memory rankings were measured on one sequence length, one node, no context-parallel path — GROUNDED, CAVEAT-ONLY (with a live exception)

Single node, `world_size=8`, `--sequence-length 4096`, `gpu-8xa100`. `recurrent.py:262` shows a
`cp_enabled`/`all_to_all_cp2hp` code path that this run never exercised (no multi-node, no CP).
The pre-registration itself (§5.1) says the R2 arm's slowness is because "it runs a **non-chunked
sequential Triton kernel**" — a property whose relative penalty is expected to *compound* at
longer sequences (less parallelism to exploit) and to *evaporate* once chunked (per #6). So
0.705×/0.779× are properties of *this* unchunked kernel at *this* 4096-token context on *this*
hardware, not stable multipliers a production run at longer context or multi-node would
reproduce — in either direction. The "fast four" (BASE/NOACT/GCONV/GDN2, spread 0.979–1.000×) are
close enough to each other (2.1% spread) that a different sequence length or a multi-node
config change could plausibly re-order them; that ranking has not been stress-tested at all.

### 8. "Gated conv is a bound, not a benefit" overstates a genuinely bimodal, unresolved result — GROUNDED, CAVEAT-ONLY

`KDA_GCONV`'s per-cell values are 3.0321, 3.0392, 3.0641 — sd **0.01678**, 6.5× `KDA_NOACT`'s
sd (0.00258). Its best cell (3.03211) is **the single best cell in the entire 18-cell run**,
beating every `KDA_NOACT` seed; its worst cell is worse than every `KDA_NOACT` seed. The
attributable contrast, `KDA_GCONV − KDA_NOACT` (`REPORT.md` §2.6), is **exploratory,
uncorrected**: +0.00511 nats, CI [−0.0312, +0.0414], p = 0.765 — a coin flip in either direction,
not a "bound." Calling this "a bound, not a benefit" is a real reading of the point estimate's
sign, but the honest statement (which the report gives correctly elsewhere: "a null is a bound,
not equivalence") applies here too and got dropped in the plain-language summary. A gate whose
best replicate beats everything else in the study deserves "unresolved, high-variance," not a
one-directional dismissal.

### 9. Attack-then-defend the null itself (assignment task 4) — GROUNDED, presented both ways

**The case that the null is an artifact of pooling:** GDN2's three seeds (3.0838, 3.0910, 3.0905,
sd 0.00404) are **all individually worse than all three `KDA_BASE` seeds** (3.0421, 3.0632,
3.0488) — complete separation between the two groups, zero overlap, and the smallest within-arm
sd of any treatment arm. Pooling GDN2's tight, well-behaved variance into a 12-df estimate
dominated by `KDA_R1`'s sd = 0.04516 (17× `KDA_NOACT`'s) inflates GDN2's effective SE by ~5×
relative to what a GDN2-vs-BASE-only test would use. A same-family two-sample test using only
these two arms' own variances would very likely resolve this contrast — the ANOVA's power is
being spent, in part, on absorbing one unstable arm's noise into everyone else's error term.

**The honest counter-case:** the pre-registration commits to pooled-variance ANOVA specifically
*to avoid* the alternative failure mode (arbitrary pairwise tests spending only 2 df each instead
of 12), and Levene's own test (the pre-committed homogeneity check) does not reject at p = 0.484
— meaning the data do not, by the designated test, support treating `KDA_R1` as categorically
different variance from GDN2's. At n=3 per arm, Levene has essentially no power to detect real
heterogeneity (stated explicitly in `REPORT.md` §2.2), so "it didn't reject" is weak license to
pool, not strong evidence pooling is correct. Both readings are defensible; the report's choice
to lead with the pooled null while relegating the seed-level total-separation fact to a table is
a framing choice, not a forced one.

### 10. Process corners: the analysis was produced same-night with no slack, and one pre-committed measurement was silently dropped — GROUNDED, CAVEAT-ONLY

Git history for `docs/mixer-bakeoff/`: GDN2 merged 04:41, seed schedule frozen 04:45, results
landed 09:13, PDF table 09:26–09:30, handoff written 09:47 — all on **2026-08-08**, all within a
run whose own token budget was already cut (1,907 → 1,144 steps) to fit a capacity/deadline
window. That is a ~5-hour arc from "GDN2 exists in the tree" to "final recommendation
published," with the entire statistical write-up (ANOVA, Dunnett, Levene/Bartlett, MDE, the
gate-isolation contrast) produced in well under an hour after the last cell landed. Separately
and concretely: `sliced_eval` (the pre-registered secondary endpoint) is null on all 18 cells
because `--slice-mask-uri` was never passed (see #5) — a corner that was cut without being framed
as a corner in the recommendation's summary (it is disclosed, correctly, in `REPORT.md` §5, but
does not appear in the four-line recommendation under attack).

## Speculative / low-priority (not decision-grounded — flagged, not pressed)

- **SPECULATIVE:** the exactly-zero within-arm sd on `peak_memory_gib` (`REPORT.md` §3.1, all six
  arms) is consistent with a deterministic caching allocator on a fixed static graph and is
  probably not a red flag — but it hasn't been independently confirmed that
  `torch.cuda.max_memory_allocated()` on rank 0 is representative of the highest-watermark rank
  under FSDP sharding (it could differ by rank if sharding is uneven). Not verified either way
  here.
- **SPECULATIVE:** whether the LR schedule (`CosWithWarmup`) was re-tuned for the shorter
  1,144-step budget or simply ran the original 1,907-step schedule truncated. If the latter, every
  arm ends short of full anneal, which would inflate all CE magnitudes roughly uniformly (already
  disclosed as a caveat) but could also interact non-uniformly with arms that have different
  optimization dynamics (e.g., the reflection-regime arms) — not verified from the artifacts
  available.
- **SPECULATIVE:** MFU is computed against `device_peak_bf16_flops = 312 TFLOPS`, correct for
  A100 (the project has a documented history of an MFU calculation silently assuming A100 peak
  on non-A100 hardware — see `moe-mfu-366-not-469.md`/`peak-memory-was-last-step-not-peak.md`
  precedents) — but this run's GPU field confirms `NVIDIA A100-SXM4-40GB` on every cell checked,
  so that specific trap does not appear to apply here. Flagged only because it's a recurring
  failure mode in this project, not because evidence of it was found in this run.

## The single most likely way this recommendation is wrong

**GDN2 is being excluded on a statistical technicality the study's own pre-registered decision
rule does not support, while the arm that technicality excludes has the highest MFU, near-tied
throughput and memory with the recommended arms, and a CE deficit that (per this project's own
in-tree precedent on how these exact kinds of effects behave with token budget) is the single
number in the whole table most likely to shrink toward zero at production scale.** Strip "GDN2 is
worse" out and the recommendation stops being "ship BASE/NOACT, reject everything else" and
becomes "throughput and memory don't distinguish BASE, NOACT, and GDN2 at all, and CE doesn't
either" — a three-way tie, not a two-way one, and the tie-breaker (does GDN2's extra API surface
— decoupled erase/write gates — matter for recall or decode?) is exactly the measurement (#4, #5)
that was never taken.

**Cheapest experiment that would expose it:** re-score the existing checkpoints (already sitting
in S3 per HANDOFF ⓺, no retraining required) against a slice mask focused on
recall/retrieval-style spans — the pre-registered secondary endpoint that was never wired
(`--slice-mask-uri`, #5). This costs a read pass over held-out text at inference cost only (the
report's own words: "zero extra training cost"). If GDN2 and `KDA_BASE`/`KDA_NOACT` separate on
that slice the way Zoology's precedent predicts (recall-attributable share of the gap rises even
as aggregate CE flattens), the "GDN2 is worse" call is validated on the metric that actually
matters for production rather than on a contested variance test. If they don't separate, the
three-way throughput/memory tie stands and the decision is genuinely a coin flip that should be
broken by a cheap decode-latency/decode-memory microbenchmark instead (also unmeasured, also far
cheaper than another 18-cell training run).
