# B2 — Arm-mechanism audit: mixer bake-off (edullm/mixer-bakeoff)

Run sha audited: `9425fea` (full `9425fea83e8f4290feb89203d49a884659b77d3b`), read exclusively via
`git show 9425fea:<path>` per the read-only rule. Current branch HEAD `f46e3b1` differs from
`9425fea` only in post-run docs/analysis (`docs/mixer-bakeoff/*`, `scripts/analyse_bakeoff.py`,
its test) — none of the arm/mixer code changed, verified by walking the intervening log.

**Bottom line up front:** all six arms build the mechanism their name claims, and the registry
correctly isolates the six named contrasts at the config level. The two things that undercut
confidence are not mislabeling — they are **unverified verification**: (1) the one test that
checks the *actual Triton kernel path used in training* for causality has no evidence of having
run before this bake-off's GPU spend, and (2) the parameter ledger the whole 0.05%-tolerance
width-match rests on is never checked against a really-built model for any of the six arms, only
against a hand-copied constant of the same formula.

## Finding 1 [UNSUPPORTED, highest severity] — the only causality check on the fused kernel has no evidence of having run

`src/test/nn/transformer/core6_bakeoff_guards_test.py` (sha `9425fea`) contains three GPU-gated
guards (`requires_gpu`, `requires_fla`) written specifically because the CPU ledger in
`core6_arms_test.py` "cannot prove they *compute* the right thing" (file docstring, lines 1-30).
Guard 1, `test_the_fused_kernel_is_causal` (lines 134-171) and its varlen sibling (177-216), is
the **only test in this repository that exercises the fused Triton kernel path with
`use_fla=True`** — "Every existing causality test in this repo runs `use_fla=False`... The fused
Triton kernels are what the bake-off measures, and their causality has never been asserted by
anything" (lines 9-12). It checks bit-exact zero leakage across a perturbed position, both
in-sequence and across a packed document boundary (the varlen branch training actually takes).

The file's own docstring (lines 23-29) states plainly:

> "These guards are written to run on the GPU host and their fireability was **NOT verified** on
> the laptop that wrote them... Run this file on the host before the arms launch."

I searched the tree at `9425fea` for any wiring of this file into a pre-launch gate, CI workflow,
or the run submission itself:
```
git grep -n "core6_bakeoff_guards" 9425fea -- .        # zero hits outside its own file
git ls-tree 9425fea:.edullm                             # no reference to the guards file
git grep -ln "bakeoff_guards" 9425fea -- .github         # zero hits
```
`.edullm/rehearsal.md` is unrelated (it documents a platform-submission-path rehearsal, not model
guards). **I found no in-repo evidence that `core6_bakeoff_guards_test.py` was executed against
this sha before the 18-cell run launched.** This does not mean it wasn't run — a human could have
run it manually on a GPU host per its own instructions, and that would leave no trace in `git`.
But absent that corroboration, the state of the evidence is: the one check capable of catching
"a mixer that reads one position into the future [and] trains stably, converges faster than its
honest siblings, and wins the bake-off" (guard 1's own docstring, line 12) is unconfirmed for
every one of the six arms, including the two brand-new operator classes (`KimiDeltaHouseholder`,
`GatedDeltaNet2`) that never shipped in this codebase before this branch.

**Recommend cross-checking with B1** (verifying the AWS run logs) for whether this file's guards
appear in the job's stdout/stderr before training started.

## Finding 2 [UNSUPPORTED] — the parameter ledger for all six bake-off arms is never checked against a real model

`src/test/nn/transformer/core6_arms_test.py::test_config_num_params_matches_built_model` (lines
542-551) is the only test that compares the analytic `num_params()` ledger to
`sum(p.numel() for p in model.parameters())` on an actually-built module. It is parametrized over
exactly `["L0", "G4R0", "S14", "G0R0"]` — **explicitly excluding K2, G4R2, and all six bake-off
arms** ("K2/G4R2 are excluded only because KimiDeltaAttention asserts `has_fla()` at
construction — they are covered on FarmShare," line 546-547).

Everything else that certifies the six arms are parameter-matched —
`test_every_arm_lands_on_its_declared_delta` (112-131), `test_r1_householder_is_parameter_
identical_to_shipped_kda` (160-170), `test_gdn2_pins_the_defaults_that_invert_gdn1` (239-251),
`test_the_gated_conv_arm_pays_only_the_depthwise_price` (173-196) — computes both sides of its
assertion from the **same** `num_params()`/`mixer_params()` config-class algebra. These are real
and valuable *drift detectors* (a formula change without updating the hand-copied constant would
be caught), but none of them is a *correctness proof against ground truth* for the six mechanism-
critical arms, because the formula being checked and the formula producing the expected value are
one and the same code path.

I looked for that ground-truth check elsewhere in the tree and did not find it. The Dockerfile's
own build-time assertions (below) build a real `gated_conv=True` KDA module on `meta` device and
assert its `q_conv1d` is a `GatedCausalConv1d` (a type check), then *print* `c.num_params(512)` —
it does not compare that printed number to the built module's real parameter count. So the claim
"covered on FarmShare" is not independently verifiable from source, and per my HARD RULES I
cannot build a model (even on `meta`) to check it myself. Given `solve_widths()` derives every
arm's FFN width directly from `mixer_params()`, an error in that formula for any of KDA_R1,
KDA_R2, GDN2, or KDA_GCONV would silently break the entire premise that the six arms are
parameter-matched, and nothing in this repository closes that loop for them.

## Finding 3 [nuance, not a defect] — KDA_R1 is parameter/FLOP-identical to KDA_BASE but does NOT compute the same function

This directly answers verification point #2's literal question ("is that literally true in code,
or only approximately?"): **literally true for parameters and FLOPs, literally false for
"computes the same function."**

- Parameters: `mixer_params("KDA_R1") == mixer_params("KDA_BASE") == 4_487_248`, asserted exactly
  by `test_r1_householder_is_parameter_identical_to_shipped_kda`
  (`core6_arms_test.py:160-170`). **CONFIRMED.**
- FLOPs: `KimiDeltaHouseholder.num_flops_per_token` (`recurrent.py:~1759-1811`) gives
  `recurrent_flops = 2*(2+2*R)*state_size`, which at `R=1` reduces algebraically to
  `8*state_size = 2*4*state_size`, matching `KimiDeltaAttention`'s formula exactly. **CONFIRMED**
  by direct algebra (not test-covered, but the reduction is exact).
- "Computes the same function": **REFUTED as literally stated**, by design, in two independent
  ways:
  1. `core6_arms.py`'s `_kda_householder()` factory (lines ~175-193) **always** passes
     `allow_neg_eigval=True`, for both R1 and R2, regardless of `num_householder`. `KDA_BASE`
     leaves it at the class default `False` (`recurrent.py:687`). So `beta` for KDA_R1 lives in
     `(0,2)`; for KDA_BASE it lives in `(0,1)`. This is confirmed both in source and in
     `test_both_householder_arms_allow_negative_eigenvalues`
     (`core6_arms_test.py:224-236`). **This is intentional** — the arm's own design note states
     KDA_R1 − KDA_BASE is meant to isolate "the beta-in-(0,2) reflection regime alone," and
     `test_r1_householder_is_parameter_identical_to_shipped_kda`'s docstring says exactly this
     ("if it held only approximately, then... KDA_R1 − KDA_BASE would not be the reflection
     regime alone"). It is not a bug. But it does mean a reader who takes "R=1 ≡ KDA" to mean
     "KDA_R1 runs the same computation as KDA_BASE" is wrong, and no arm in this bake-off would
     let you isolate arity (R) alone from the reflection regime — there is no `allow_neg_eigval=
     False, num_householder=1` control arm.
  2. Independent of (1) — even at matched `allow_neg_eigval` — `KimiDeltaHouseholder.forward()`
     (`recurrent.py:1578-1688`) computes the forget gate eagerly, explicitly in float32
     (`g = -self.A_log.float().exp() * F.softplus(self.f_proj(x)...float() + ...)`, lines
     ~1631-1638) and L2-normalizes q/k explicitly via a Python-side `l2_normalize()` call, then
     dispatches to a **different kernel**, `chunk_kda_householder`. `KimiDeltaAttention.forward()`
     (`recurrent.py:839-930`) instead dispatches to `dispatch_chunk_kda(..., use_gate_in_kernel=
     True, use_qk_l2norm_in_kernel=True, ...)`, which computes the gate and normalizes q/k
     **fused, inside the Triton kernel**. The class's own comment (`recurrent.py:1631-1633`)
     states this is deliberate ("unlike `fla.ops.kda.chunk_kda` this kernel has no fused-gate
     path"). This means even a hypothetical `allow_neg_eigval=False` Householder-at-R=1 variant
     would not be bit-identical to KDA_BASE, only numerically close at a bf16 budget — consistent
     with the parallel finding in the prior probe-study audit doc
     (`docs/kda-householder/kda-householder.md`, a different commit but the same structural
     claim, which I independently reproduced against `9425fea`'s actual code rather than trusting
     the doc).

## Finding 4 [confirmed, medium severity as a latent pattern] — two optional-fast-path silent fallbacks exist, both low-risk for this specific run

Per the mandate's "silent-fallback hunt": both `GatedCausalConv1d._conv()`
(`gated_convolution.py:507-544`) and `ShortConv._conv()` (`short_conv.py:203-247`) share the
identical pattern:
```python
if self.use_fla and has_fla() and x.is_cuda:
    ... dispatch_causal_conv1d(...)   # fused Triton path
else:
    ... self._conv_dense(...)         # torch.nn.Conv1d reference path
```
with `use_fla: bool = True` as the default on both classes (`gated_convolution.py:381`,
`short_conv.py:169`/`429`). This is precisely the class of bug the prompt flagged as previously
having caused a control arm to silently run a different operator from a treatment arm.

By contrast, `flash_linear_attn_api.py` (the shared dispatch module) has **zero** silent
fallbacks: every one of its five functions (`dispatch_chunk_gated_delta_rule`,
`dispatch_chunk_kda`, `dispatch_chunk_gdn2`, `dispatch_causal_conv1d`, `has_fla`) either
`assert`s or raises `RuntimeError` when `fla` is unavailable — hard failure, not silent
degradation.

For this specific run, the risk is low but not fully verifiable from source alone:
- The Dockerfile (`9425fea`, final `RUN` block) hard-asserts `flash-linear-attention==0.5.1`,
  `fla-core==0.5.1`, a CUDA torch build, and `has_fla()` returning `True` at image-build time,
  and additionally asserts `from fla.ops.gdn2 import chunk_gdn2` and
  `from fla.ops.kda import chunk_kda` import successfully. So `has_fla()` is true in the shipped
  image.
- `run-bakeoff.yaml` submits `suggested_compute: gpu-8xa100`, a real GPU job, so `x.is_cuda`
  should be `True` at runtime.
- Given both conditions, the fused path should trigger for all six arms in practice. I could not
  independently confirm this was actually exercised (that requires a runtime trace, which is
  B1's remit on the AWS logs, not a source-read).
- Even if the fallback *did* fire: `ShortConv`'s LIV-layer configuration (`kernel_size`,
  `gate_structure="dense"`, `use_fla`) is **identical across all six bake-off arms** (all six
  declarations inherit the same LIV block spec — no arm overrides it), so a triggered fallback
  there would degrade all six arms equally, not differentially. `GatedCausalConv1d` is used by
  **only** `KDA_GCONV` (`MIXERS["kda_gconv"]` is the only entry with `gated_conv=True`), so its
  fallback, if triggered, would not create a cross-arm mismatch either — it would only mean
  KDA_GCONV's own numbers reflect the reference implementation rather than the fused one. **No
  evidence was found of the specific "two arms take different paths for the same nominal
  operation" failure mode this bake-off was checking for.**

## Point-by-point verification results

**1. `allow_neg_eigval` on KDA_R1/KDA_R2 — CONFIRMED, explicit not default.**
Class default `False` (`recurrent.py:687` for `KimiDeltaAttention`, `:1472` for
`KimiDeltaHouseholder`). `core6_arms.py`'s `_kda_householder()` factory always passes
`allow_neg_eigval=True` explicitly, with a docstring stating this in capitals as deliberate.
Confirmed independently by `test_both_householder_arms_allow_negative_eigenvalues`
(`core6_arms_test.py:224-236`).

**2. `num_householder` = 1/2, parameter/FLOP identity — CONFIRMED with the nuance in Finding 3.**
See Finding 3 above for the full analysis; short version: numbers correct, params/FLOPs
identical, computation is *not* identical (by design).

**3. `KDA_NOACT` changes exactly one thing — CONFIRMED.**
`MIXERS["kda_noact"] = lambda: _kda(conv_activation=None)` (`core6_arms.py`) — no other field
touched. `gated_conv` stays `False`, so `_build_conv()` (`recurrent.py:779-822`) takes the same
plain-`CausalConv1d` branch as `KDA_BASE`, only its activation argument differs. Zero parameter
delta, confirmed both by the shared `ARM_L0_DELTA["KDA_NOACT"] == ARM_L0_DELTA["KDA_BASE"] ==
K2_L0_DELTA` and by
`test_the_gate_isolating_contrast_exists_and_is_parameter_free` (`core6_arms_test.py:199-221`),
which also asserts `base.gated_conv is False` and `noact.gated_conv is False` — ruling out any
second thing moving with the activation change.

**4. `KDA_GCONV` wiring and the SiLU identity — CONFIRMED.**
`MIXERS["kda_gconv"] = lambda: _kda(gated_conv=True, gate_structure="depthwise")`. In
`gated_convolution.py`, `_gates()` (lines 470-505) for `"depthwise"` returns
`(2*sigmoid(pre_scale*u), 2*sigmoid(post_scale*u))` reading the convolved stream `u` itself
(`gate_source="stream"`, forced for depthwise) — a literal match for the claimed
`2*sigmoid(a*u)*u` form, and the identity `2*sigmoid(a*u)*u == (2/a)*silu(a*u)` is exact algebra
(module docstring, lines 133-186; `silu(y)=y*sigmoid(y)` substitution), not an approximation.
`forward()` (564-585) wires `post_gate * conv(pre_gate * u)`, matching the claimed prose. The
isolating-contrast test `test_the_gate_isolating_contrast_exists_and_is_parameter_free` and the
cost test `test_the_gated_conv_arm_pays_only_the_depthwise_price`
(`core6_arms_test.py:173-196`) additionally prove the shipped config is depthwise, not lowrank:
`cfg.gate_structure == "depthwise"`, per-layer cost `6,144` (arm lands at `+2,208` total), versus
a lowrank counterfactual at the same rank costing `2,359,296` (12x the tolerance) — the test
computes this counterfactual from the config's own algebra rather than trusting the "12x" figure
asserted only in prose.

**5. GDN2 uses Tom Liu's class and calls `chunk_gdn2`, not a fallback — CONFIRMED.**
`GatedDeltaNet2.forward()` (`recurrent.py:2182-2184`) calls
`dispatch_chunk_gdn2(q=q, k=k, v=v, g=g, b=b, w=w, ..., use_qk_l2norm_in_kernel=True)`.
`dispatch_chunk_gdn2` (`flash_linear_attn_api.py:130-164`) hard-`assert`s `has_fla()` then calls
`fla.ops.gdn2.chunk_gdn2` directly — no fallback. Corroborated at the image level: the Dockerfile
asserts `from fla.ops.gdn2 import chunk_gdn2` imports successfully in the shipped image.

**6. Silent-fallback hunt — see Finding 4 above.** Two latent fallback sites found
(`GatedCausalConv1d._conv`, `ShortConv._conv`), both assessed low-risk for this specific run but
not independently confirmed via a runtime trace.

**7. Attention schedule and RoPE mechanism — CONFIRMED, both halves.**
All six bake-off arm declarations (`core6_arms.py:391-479`) inherit the default
`attention_layers=ATTENTION_LAYERS=(2,5,8,10,12,14)` (none override it) and all set
`kda_layers=(6,11)`. Independently re-verified against the *built* config (not just the
declaration) by `test_every_bakeoff_arm_keeps_the_full_attention_budget`
(`core6_arms_test.py:254-272`, `idx == ATTENTION_LAYERS` for all six) and
`test_every_mixer_arm_places_its_operator_in_the_frozen_slots` (427-442, correct *class* in slots
{6,11} per arm, guarding against a mis-keyed `MIXERS` entry). The RoPE mechanism itself —
independently read, not just trusted from the arm registry's comment — lives in
`model.py`'s `get_rope_buffers` (lines 253-268): `if isinstance(block.attention, (Attention,
FusedAttention)): ... else: rope_buffers[key] = None`. `block.attention` is the literal attribute
name every `TransformerBlock` variant stores its sequence mixer under regardless of type
(`block.py:128-131`: "The `self.attention` naming is kept for backwards compatibility... could
contain any `SequenceMixer` implementation, such as a `GatedDeltaNet`") — so the isinstance check
correctly identifies genuine attention blocks and gates RoPE on it. This is a different, correct
use of `.attention` than the "block.sequence_mixer not .attention (silently no-ops)" trap
recorded in project memory, which concerns code that tests for the *attribute's presence* rather
than *type-checking its value* as here.

**8. `solve_widths` fix presence and tolerance — CONFIRMED, strongly.**
The mixer-size correction (`surplus += len(arm.kda_layers) * (mixer_params(arm) -
_BLOCK_PARAMS["kda"])`) is present in `core6_arms.py` at `9425fea`, traced to its introduction at
ancestor commit `eb04f03` ("Merge GDN2, and put the fla version in exactly one place"), confirmed
an ancestor of `9425fea`. Beyond presence, there is a **named regression test reproducing the
exact historical bug**: `test_the_solver_is_what_holds_the_big_mixers_on_the_anchor`
(`core6_arms_test.py:134-157`) computes what KDA_R2 and GDN2 *would* deviate by without the
correction (surplus / `L0_PARAM_TARGET`) and asserts it exceeds `20 * WIDTH_TOLERANCE` — the test
file's own docstring says "some 21x outside it," matching the magnitude in project memory almost
exactly, and computes the counterfactual from the raw mixer sizes rather than a second copy of
the solver, so it "cannot pass by re-deriving the formula it is checking." Every arm's *declared*
delta is asserted **exactly** (not a tolerance band) via `test_every_arm_lands_on_its_declared_
delta` (112-131), and every arm's *tolerance* compliance is separately asserted via
`test_every_arm_is_within_the_declared_tolerance` (275-283, `WIDTH_TOLERANCE = 5e-4`). See
**Finding 2** above, however: none of this closes the loop against a really-built model for the
six bake-off arms specifically — the ledger is internally consistent and drift-guarded, not
ground-truth-verified in this repository.

## Summary table

| Arm | Is it the mechanism its name claims? | Caveats |
|---|---|---|
| KDA_BASE | Yes | — |
| KDA_NOACT | Yes | Confirmed parameter-free, single-field change |
| KDA_GCONV | Yes | Depthwise confirmed, not lowrank; SiLU identity exact |
| KDA_R1 | Yes, for R=1 and the reflection regime | Params/FLOPs exactly match KDA_BASE; **computation does not** (different kernel, eager fp32 gate, forced allow_neg_eigval=True) — intentional, but "R=1 ≡ KDA" should not be read as "same computation" |

No two arms were found to silently diverge in an *unlabeled* way. The two open risks (Findings 1
and 2) are gaps in verification coverage, not evidence of mislabeling — but both sit exactly
where a mislabeling-class error would be invisible in a loss curve, per this repo's own stated
design philosophy, so I am not calling them low-severity.
